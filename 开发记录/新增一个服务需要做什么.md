# 新增一个服务需要做什么（T5 交付 · T6 补记 ★）

> 一句话：**只写两个文件（一份 YAML + 一组模板），不改 `app\` 一行代码。**
> 这份清单是 T5 把 Nginx 从零做到"能跑、能幂等、能卸载"的**全过程抽象**，
> 每一条后面都跟着"**不这么做会怎样**"——那些坑全都是真跑时踩出来的。
>
> ★ **T6 用同一份清单又做了三个服务（MariaDB / Valkey / NFS）**，结论见 §7：
> 清单本身**站得住**（三个服务一次通过，引擎零改动），但要再补五条"只有第二个、第三个服务
> 才会逼出来"的东西。★ 其中两条（配置钩子、生效动作）是**服务自身的差异**，
> 两条（建目录、`{{ }}` 陷阱）是**模板机制的边界**，一条（既有包）是**靶机纪律**。

---

## 0. 先确认三件事（花 5 分钟，省半天）

| # | 确认什么 | 怎么确认 |
|---|---|---|
| 1 | 这个服务要跑在**哪台机器**上，那台机器**允许动什么**（包？哪个目录？哪个端口？） | 看 `hosts.yaml` 的 `note` 与当前阶段开题单的「靶子纪律」 |
| 2 | 它的**配置校验命令**存在吗（`nginx -t` / `sshd -t` 这类） | 你的服务若不在 `svc.configtest` 的枚举里，**先扩那个枚举**（那是平台改动，要走规范） |
| 3 | 它的**反向操作**能不能干净地做出来（停 / 保留数据卸载 / 全删卸载） | ★ 做不出来就别开始 —— 只写正向的配方**不合格**（规范 §12.6，宪法 3） |

## 1. 写配方：`repo\catalog\recipes\<id>.yaml`

照 `nginx.yaml` 抄，逐段填。字段语义的唯一依据是 **`docs\动作规范.md` §12**。

| 段 | 填什么 | ★ 不这么做会怎样 |
|---|---|---|
| `id` / `name` / `version` / `summary` / `risk` | `version` 是**配方自己的版本**（改配方就 +1），**不是包版本**；`risk` 取步骤里最严的那一级 | 把 `version` 写成包版本 → 包一升级，配方里就留着一个查不到的版本号自欺（§12.1.1） |
| `params` | 5~8 个填空题。**必须给 `pattern` / `min` / `max`** —— 那就是第一道安全边界 | 只给 `type: int` → 人填 `999999` 也能过，然后靠失败去发现 |
| `preflight` | **只放"部署前后都成立"的事实**（例：这台机器上不该有 `httpd`） | ★ 放 `absent(pkg.installed <自己>)` 或 `free_port` → **第二次跑必然中止**，而幂等要求第二次跑**成功且零变更**（`nginx.yaml` 的 `note` 里写清了这段推理） |
| `steps` | 引用**已登记的动作**；写文件用 `template:` + `dest:` | 写 `run:` / 命令 → 装载期直接拒（配方里不许有命令，这是宪法 1） |
| `health` | "**部署完了到底能不能用**"。用 `state: active` + `http_status`（或你这个服务等价的判据） | 没有 health → 装载期直接拒。**"命令返回 0" 不是可用性** |
| `uninstall` | `stop` / `disable` / `remove_config` / `purge_paths` / `keep_data` / `remove_packages` / 两个确认词 / `health` | 见第 3 节，这里坑最多 |

### 1.1 覆盖既有文件前，别忘了"改了才重启"

```yaml
  - name: render_conf
    template: <svc>/<file>.conf
    dest: /etc/<svc>/<file>.conf
    notify: [restart_<svc>]          # ★ 只有"内容真的变了"才触发
  - name: restart_<svc>
    action: svc.restart
    args: { unit: <svc> }
    trigger_only: true               # ★ 跑配方时不会无条件执行
```

`trigger_only` **必须写** —— 否则装载期拒绝，而且你会得到一条"每次都重启"的抖动配方。

## 2. 写模板：`repo\catalog\templates\<svc>\*`

- 占位符 `{{ 参数名 }}`（**纯替换，零逻辑**；不引 Jinja2，规范 §12.4）
- 要写**真的** `{{` → 用 `{{ '{{' }}`（本话题定死的唯一转义语法）
- ★★ **说明文字里的裸 `{{ }}` 也会被当成占位符**（T6·S4 真跑踩到）：
  我在 `nfs/README.txt` 的注释里写了「与 Nginx 用 `{{ root_dir }}/index.html` 建目录同一姿势」，
  渲染期直接报 `TEMPLATE_PARAM_MISSING：模板引用了未定义的参数 root_dir` ——
  **模板里没有"注释"这种东西，整份文件都是模板**。想写占位符的样子，就用上面的转义语法，
  或者干脆别写花括号（我最后就是改成文字描述）。
- **缺必填参数 → 报错中止**，绝不静默写成空值
- 服务自己的 `$变量`（如 nginx 的 `$remote_addr`）**不受影响**，照写
- 同名文件**不要**放在 `dest` 的父目录里手工改 —— 那份文件由配方管，手改会在下次部署被覆盖（这是"幂等"的正常含义）

## 3. ★★ 反向操作：四个坑（T5 全踩过，全修了）

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | **`remove_config` 写了包自带的目录**（如 `/etc/nginx`） | ★★ **只删"配方自己写出来的文件"**（`/etc/nginx/nginx.conf`）。删掉包目录会把 `mime.types` 这类 rpm 管的文件一起干掉 → **包进入残缺状态**，`nginx -t` 永久报 `open() "/etc/nginx/mime.types" failed`，而**重跑配方只能重写它自己管的那一个文件，修不回来**（要靠 `dnf reinstall` 或恢复备份）。包目录留给 `purge_paths`（全删时包也会卸） |
| 2 | **`uninstall.health` 用 `state: {equals: inactive}` 判"停干净了"** | ★★ 用 **`free_port: "{{ port }}"`**。`svc.disable` 会让 systemd 把单元**从内存卸载**（`systemctl list-units --all` 也查不到），`svc.list` 自然列表里就没它了 → 判定成"系统里没有这个服务" → **明明停得干干净净却判红**。`state` 只适合判 `active`（"起来了没有"），不适合判"停了没有"（规范 §12.6.3） |
| 3 | **拿部署段那句 `state: active` 去判 `stop`** | 反向操作要么声明自己的 `uninstall.health`，要么干脆不判健康 —— 判据与被判的动作方向相反，等于把"做成了"判成"失败"（规范 §12.6.3） |
| 4 | **`keep_data` / `purge_paths` 里写 `{{ 参数 }}`，却指望报告念真值** | 平台已经帮你渲染（结论 / 计划 / 确认框都给真值）—— 但**你自己写的 `note` / `fail_reason` 文案里不要手写路径**，一改参数文案就错了 |
| 5 | **直接调 `red` 动作时，填错确认词**（T6 踩到） | ★ 两头确认词**不是同一个**：`svc.stop` 这个**动作自己**要的是「我已确认要停止」；**配方**声明的是 `stop_confirm_text`「我已确认要停止服务」，人输的是后者，平台**自动把内层动作的确认词转达下去**（`confirm_relay` 留证）。⇒ 你的配方只要声明好两个词；**别在脚本里拿配方的词去直调动作**（会 `CONFIRM_REQUIRED`） |

**一条老坑（T3 遗留，T5 才现形）**：目录型备份的**恢复**原来用 `cp -a <备份目录> <原路径>`，
目标是目录且已存在时会**多套一层**（恢复出 `/etc/nginx/00-nginx/…`）——
报告写着"已恢复"、其实一个文件都没还原。已修（`cp -a <备份目录>/. <原路径>/` + 逐文件指纹汇总自证，规范 §9.2）。
**你要是做"删目录再恢复"的服务，记得照着验一遍**。

## 4. 跑一遍（每一步都能停、能看）

```powershell
cd E:\LOBEHUB_work\项目库\auto-ops-console\repo
$env:PYTHONIOENCODING='utf-8'
python -m app.server --check        # ★ 先看装载校验：坏的配方在这里就被拒，并说清原因
python -m app.server                # 起控制台（页首应显示当前阶段与版本）
```

界面「服务目录」页签 → 点你的配方 → 你会看到：参数表单 / 前置检查 / 普通步骤 / **条件步骤（单独列出）** /
健康检查 / 五个按钮（部署・收敛 / 检测当前状态 / 停止 / 卸载·保留数据 / 卸载·全删）。

**验收顺序（照做，别跳）**：

1. **缺必填 / 越界** → 必须报错，不许静默写空值
2. **第一次部署** → 变更清单应当是"该变的都变了"
3. ★ **原样再跑一次** → `changed_steps` **必须为空**（这才是幂等证明；受管文件 sha256 前后一致）
4. **改一个参数再跑** → 应当恰好那一步"变了"，且被 notify 的步骤**真的跑了**
5. **故意让某步失败**（占端口最简单）→ 报告要给出「失败在哪步 + 可回滚到哪个检查点 + 一键恢复」，
   并**真的点一次恢复**、核对 sha256
6. **停止** → 判据是"端口没人听"，且**配方判 ok**（不是失败）
7. **卸载·保留数据** → 用平台动作**真去验** `keep_data` 里那些路径还在
8. **卸载·全删** → 手输确认词；完了把机器装回来，再跑一次第 3 步

## 6. ★ T6 补记（MariaDB / Valkey / NFS 真跑逼出来的五条）

> 这五条不是"再来一遍要小心"，而是**每加一个新服务都会先撞上**的判断题。
> 顺序就是判断顺序：**① 我的配置写在哪 → ② 改完靠什么生效 → ③ 目录谁来建 → ④ 端口钉几个 → ⑤ 包是不是我装的。**
> ★ 结论先行：**清单本身站得住** —— 三个服务都是"一份 YAML + 一组模板"，**引擎零改动**；
> 下面这些是"第二个、第三个服务才会露出来"的服务差异与机制边界。

### 6.1 ★★ "我的配置文件写在哪" —— 找服务**自己留的钩子**，别动包自带的文件

同一个问题，三个服务三种答案（T6 实测）：

| 服务 | 它的钩子是什么 | 我们写哪 | 为什么 |
|---|---|---|---|
| MariaDB | `/etc/my.cnf.d/` 是**drop-in 目录**（包自带） | `/etc/my.cnf.d/aoc.cnf` | 目录本来就被 `!includedir` 读走 |
| Valkey | 包**没有** drop-in 目录（`valkey.conf` 里的 `include` **全是注释**）；但**单元自己留了钩子**：`EnvironmentFile=-/etc/sysconfig/valkey` ＋ `ExecStart=… $OPTIONS` | `/etc/sysconfig/valkey`（写 `OPTIONS="--port …"`） | ★ 那个文件**默认不存在**（实测），是**纯我们自造的**；写进去 ≈ 改 `valkey.conf` 里那一行，却**一个字的包文件都不动** |
| NFS | `/etc/exports.d/*.exports` 是**导出目录**（包自带） | `/etc/exports.d/aoc-<名>.exports` | 与系统自带的 `/etc/exports` **并列**被读走 |

★ **一条硬规矩**：**永远不要写包自带的那份主配置**（`/etc/valkey/valkey.conf`、`/etc/nginx/nginx.conf`…）——
理由与 §3 坑 1 同源：那份文件里的几十行默认值 **`remove_config` 复原不了**，卸一次就成残缺的包。
**找不到钩子时**：先读单元文件（`EnvironmentFile` / `ExecStart` 里的变量 / `ExecStartPre`），
再看包有没有 `*.d/` 目录；两样都没有，**先升规范再决定**（T6 把"写自己的 conf ＋ systemd drop-in"这条路**实测过并否掉**，见 §6.2）。

### 6.2 ★★ "systemd drop-in 这条路，本工作台走不通"（T6 实测，别重走）

没有 drop-in 目录时，直觉方案是：写自己的 conf ＋ 用 `/etc/systemd/system/<unit>.service.d/aoc.conf`
覆盖 `ExecStart` 指过去。**T6 实测不行**，两条原因缺一不可：

1. **平台没有 `daemon-reload` 能力** —— 全库 47 个动作里**没有任何一个**做 `systemctl daemon-reload`
   （它只出现在 `var/lab/` 的实验室脚本里）。新写上去的 drop-in **systemd 看不见**，
   `svc.restart` 用的是**内存里那份旧的**单元定义；
2. ★★ 更糟的是**这会制造假绿**：drop-in 没生效 → valkey 照样用包自带配置跑 → 端口在、`PING` 有应答 →
   健康检查**全绿**，而我们那份配置**一个字都没被读过**。而现在的 `expect` 判据里
   **没有任何一种能证明"我们那份配置真的被读了"**（`state` / `port_open` / `responds` 都是"服务活着"的证据）。

★ 所以：**选能"被证伪"的那条路**。`/etc/sysconfig/valkey` 之所以对，正是因为它**写坏了会红**：
T6 把 `OPTIONS` 写坏一次 → `valkey-server` **真的起不来** → `svc.restart` 判 failed、探针 **3/3 判红**。
**一条配置写法好不好，看它写坏了会不会红**（与 §9.13 / 检查清单 46 同一把尺子）。

### 6.3 ★ "让配置生效"那一下，先查单元自己有没有在做

NFS 的导出**不是 systemd 动作**（是 `exportfs`），直觉是要新增一个 `nfs.export` 动作。T6 查到的正解：

```
# systemctl cat nfs-server | grep ExecStartPre
ExecStartPre=-/usr/sbin/exportfs -r        ← ★ 单元自己已经在做
```

⇒ **`svc.restart nfs-server` 本身就等价于"让导出生效"**，本话题**不新增动作**（规范 §12.12）。
★ 规矩：**做新服务前先 `systemctl cat <unit>`**，把 `ExecStartPre/Post`、`EnvironmentFile`、
各个 `Exec*` 读一遍 —— 你要"补"的那只手，很可能单元已经长了。
★ 顺带记住那个 `-` 前缀：`ExecStartPre=-…` 意思是**失败了也继续启动**。
所以"导出配置写坏了"不一定能让服务起不来 ⇒ **健康检查必须去问链路最末端**
（NFS 用 `showmount -e 127.0.0.1`：问本机 mountd"你现在到底导出什么"，而不是"配置文件写对了吗"）。

### 6.4 ★ 目录谁来建：模板写入自带 `mkdir -p`，往目录里写一个文件就是"建目录"

平台**没有**「建目录」这个动作（也不该有 —— 那等于开一条命令通道）。但模板写入前会
`mkdir -p <dest 的父目录>`（`app/engine.py`）。⇒ 建目录的姿势是：
**往那个目录里写一个正经文件**（Nginx 写 `index.html`、NFS 写 `README.txt`）。

★ **顺序有讲究**：NFS 的导出目录必须在"导出配置生效"**之前**存在，
否则 `exportfs -r` 会因为"目录不存在"报错。步骤顺序要按这个来排。
★ 顺带：你写进目录的那个文件**不是装饰** —— 它就是"目录已就绪"的证据。

### 6.5 ★ 端口按"整组"钉；包先分清"是不是我装的"

- **端口**：一个服务往往不止一个端口。NFS 实测是 **2049（nfsd）＋ 20048（rpc.mountd，UDP）＋ 111（rpcbind）**。
  只钉 2049 抓不到"导出配置生效了、但 mountd 没起来"这种**半死状态**。
  ★ 但**别瞎钉**：先真机把服务起来、再看 `net.port` 实际在听什么，然后照着写（T6 就是这么定的 20048）。
- **包**：`install` 步骤显示"未变更"的包，可能是**系统本来就装着**的（NFS 的 `nfs-utils` 就是，
  2026-08-09 装的）。这不影响配方正确性，但影响**收尾还原**：
  全删会把它卸掉 ⇒ 收尾时**要把系统原有的装回去**（别把靶机越还原越缺东西）。

## 8. ★★ T7 补记：现在"加一个服务"这件事本身也被工具化了

T7 之前，上面那六节是**给人读的**；T7 之后有三样东西**替你把它们变成工序**（规范 §12.17 / §12.21）：

| 工具 | 一句话 | 用在哪一步 |
|---|---|---|
| **热装载** | 改完 `catalog/recipes/*.yaml`，点「服务目录 → 重新装载配方」**即可生效**，**不用重启控制台** | 第 1~2 节（改配方的时候） |
| **脚手架** | `python tools\new-recipe.py <id> --unit … --package … --port … --config … --data …` 生成一份**能直接过装载校验**的骨架 | 第 1 节（从哪开始） |
| **配方体检** | 服务目录里点「配方体检」（`GET /api/recipes/<id>/lint`）—— **不连目标机**，只回答"写全了没有 / 判得出来没有" | 第 4 节之前（别等跑出奇怪的失败） |

### 8.1 ★ 用脚手架的一个真实样例（T7·S5 的现场证据）

```powershell
cd E:\LOBEHUB_work\项目库\auto-ops-console\repo
python tools\new-recipe.py aoc-httpd --unit httpd --package httpd --port 8085 `
    --config /etc/httpd/conf.d/aoc.conf --data /var/www/aoc-httpd --name "Apache httpd（自写配方样例）"
```

它会生成**两份**文件（配方 + 它引用的模板），然后你要按骨架里那 **7 处 `★ TODO`** 逐条填空：

| TODO | 骨架里问的是什么 | `aoc-httpd` 填的答案 |
|---|---|---|
| ① 配置文件写在哪 | 找**服务自己留的钩子**（§6.1） | RHEL 的 `httpd.conf` 末尾有 `IncludeOptional conf.d/*.conf` ⇒ 我们只往 `/etc/httpd/conf.d/` 放**自己的** `aoc.conf` |
| ② 怎么生效 | 改了配置靠什么生效 | httpd 要重启才重读 `conf.d` ⇒ `notify` 唤起 `svc.restart` |
| ③ 健康检查"真问一句" | 骨架默认只有 `state` + `port_open`（**旁证**） | 补 `http_status: 200`（★ 这才是"站点真能返回页面"） |
| ④ 哪个目录是数据 | 要进 `keep_data` | `/var/www/aoc-httpd` |
| ⑤ 前置护栏 | 骨架给的 `absent: httpd` 是**示例** | 按说明**整段删掉**（不改成假闸门：nginx 与 httpd 并不冲突） |
| ⑥ 包名 | | `httpd`（不是 `apache2`） |
| ⑦ 模板内容 | 骨架给的 `port = {{ port }}` 是占位 | 换成 Apache 真正认的 `Listen` + `<VirtualHost>` |

★ 填完之后：**重新装载配方** → **配方体检**（总判 `warn`：只有一条"没写 preflight"，那是真的没写）→
**部署**（6 项变更、健康检查 3/3 通过）→ **原样再跑**（`changed_steps` **为空**）→ **全删**（收敛 3/3）。
★ 全程**没有改一行平台代码** —— 这就是"扩展点"该有的样子。

### 8.2 ★★ 体检会替你看的七件事（照它改，别照它吵）

`反向操作（停/撤自启/删配置/删目录/卸包/保留数据承诺）` · `前置护栏` ·
**`健康检查是不是只有旁证`** · **`幂等可断言（能变更的步骤有没有 changed 规则）`** ·
`可回滚点` · `参数（必填无默认值）` · `批量闸门`。

★ 三态就是三种处理方式：`ok` 不用管 · **`warn` 是"能跑，但有条边界要知道"**（例如没写 preflight、
健康检查只有旁证）· `fail` **别拿去跑**。

### 8.3 ★ 写坏了会怎样：`var\lab\recipes-bad\` 三份反例

那三份是**故意写错**的配方（把命令写进配方 / 卸载段不完整 / 引用不存在的东西），
用途是让你（和自检）确认"装载期校验真的会拒、而且拒的理由**指名道姓**"。看 README 里的用法。

★ 一句话（T7 之后）：**加一个服务 = 脚手架生成 → 按 7 处 TODO 填空 → 重新装载 → 体检 → 部署 → 幂等 → 全删。**
上面那八条验收没变，只是现在**每一步都有工具替你盯着**。

---

## 9. 一句话总结

> 加一个服务 = **一份 YAML + 一组模板 + 这张清单上的八条验收**。
> 真正难的不是"怎么装这个服务"（那是几条命令），而是三件事：
> **① 判定不许写进 YAML ② "没变"必须可断言 ③ 每个正向步骤都要有反向操作。**
> 这三件做对了，Docker / MySQL / Redis / NFS 就只是"再写几份 YAML 和模板"。
