## 2. 目标（四条主线）

### 主线 1：★ 把"加一个服务"从"跑通一次"变成"**可复制的工序**"

T5 交付了一份《新增一个服务需要做什么》（八条验收）。T6 要证明的**不是"我还能做服务"**，
而是**那张清单照着做第二遍、第三遍也对**，而且：

- **引擎一行不用改**（除"把新服务的配置校验命令加进 `svc.configtest` 的枚举"，那是计划内的平台改动）
- 每加一个服务，**六条验收都必须重新走一遍**（缺必填报错 / 部署 / **第二次零变更** / 改参数只动该动的 /
  故意失败给回滚指引 / 三个反向按钮）
- ★ 如果发现"必须改引擎才能加服务" → **那是本话题最有价值的产出**：说明 T5 的抽象有漏，
  要**先补规范、再改引擎**，并把它写进清单

### 主线 2：服务目录铺量（按 §10 拍板后的清单）

每个服务一份 `catalog/recipes/<id>.yaml` + 一组 `catalog/templates/<id>/*`，**不写新动作**（除非确有必要，见 §3.5）。

| 服务 | 配方 id（建议） | 关键动作 | 反向操作 | 备注 |
|---|---|---|---|---|
| MariaDB（代 MySQL） | `mariadb` | `pkg.install mariadb-server` → 渲染 `/etc/my.cnf.d/aoc.cnf` → `svc.configtest`? → `svc.start`/`enable` → 健康检查（端口 + `mysqladmin ping`） | 停止 / 保留数据（保 `/var/lib/mysql`）/ 全删 | ★ `svc.configtest` 目前只认 `nginx`/`sshd`，**要扩枚举**（见 §3.5） |
| Valkey（代 Redis） | `valkey` | `pkg.install valkey` → 渲染 `/etc/valkey/aoc.conf` → `svc.start`/`enable` → 健康检查（端口 + `PING`） | 同上 | ★ 注意：`valkey` 提供的是 `valkey-server` / `valkey-cli`，**要实测有没有 `redis-server` 兼容名** |
| NFS 服务端 | `nfs` | `pkg.install nfs-utils`（已装则零变更）→ 渲染 `/etc/exports.d/aoc-<名字>.exports` → （`exportfs -ra` 要不要做成动作？见 §3.5）→ `nfs-server` 启动/自启 → 健康检查（本机 `showmount -e` 验证导出确实生效） | 停服 / 保留数据（保导出目录内容）/ 全删（删导出目录 + 撤导出） | ★★ **绝不能碰 `/data/nfs`**；导出点建议 `/srv/aoc-nfs/<名字>`；端口 2049 + 20048 + 111 |
| Docker（**看拍板**） | `docker`? | 若做：`pkg.install docker-ce` → `svc.start/enable` → 健康检查（`docker info` + `docker ps`） | 停服 / 全删 | ★ 三个 K8s 节点上 docker 是 **disabled 而 cri-docker.socket 是 active** —— 启它**可能影响 k8s 运行时**（灰色地带，必须拍板） |

### 主线 3：★ 双引擎（包管理 / 容器）的取舍与默认值 —— **在一张表里说清"为什么"**

不要写"推荐包管理"这种话，要写成**可执行的规则 + 现实依据**：

| 维度 | 包管理（dnf） | 容器（docker/podman） |
|---|---|---|
| 本环境可行性 | ✅ 源可达（Rocky 官方） | ❌ 公网不可达、Harbor 无业务镜像 |
| 交付物形态 | 包 + `/etc` 配置 + systemd 单元 | 镜像 + 容器 + 卷 |
| 反向操作 | 停 / 保留数据（保 `/var/lib/*`）/ 全删（卸包 + 删数据） | 停 / 删除容器（保卷）/ 删除容器+卷+镜像 |
| 哪些服务**只能**容器 | —— | K8s 相关组件、Harbor 自身（现成例子） |
| 默认值建议 | ★ **服务类（DB / 缓存 / 存储）默认包管理**；**"跑一个别人的镜像"才用容器** | 需要多版本并存 / 隔离时才上容器 |
| 让 T6 决定的具体问题 | 三个新配方**全部走包管理**；`docker` 本身**是否纳入**见 §10 #3 | —— |

### 主线 4：界面的"服务目录"要能承载多个服务

现在（T5）服务目录页签是一个**配方卡片列表 + 点进去的详情页**。T6 加 2~3 个配方之后，要检查：

- 列表是否还能一眼看清"每个服务现在是什么状态"（靠 `last_run` + `probe`）
- ★ **多服务并存时会不会互相干扰**（端口/目录/服务名冲突）—— 这是"铺量"才会暴露的问题
- 如果发现不够用 → 先补规范（§11）再改界面

## 3. 范围（做什么）

### 3.1 规范升级 v1.7（S0，铁律：先规范后代码）

见 §11。**动 `app\` 核心代码之前**必须先补。

### 3.2 每个服务一个配方 + 一组模板（主线 2 的表）

每份配方必须满足 T5 那份清单的**全部八条**，并且：

- `risk` 取步骤里最严；含 `red` 动作（`file.remove`/`svc.stop`/`pkg.remove`）必须声明两个确认词
- `uninstall.remove_config` **只列配方自己写出来的文件**（T5 的教训：写包自带目录 = 包残缺）
- `uninstall.health` 判"停了没有"用**外部可观测判据**（端口/探测），**别用 `state: inactive`**（T5 的教训）
- 模板里只 `{{ }}` 纯替换，缺必填**报错中止**

### 3.3 补齐"服务从装到可用"的健康检查手段

Nginx 有 `nginx -t` + HTTP 探测。MariaDB / Valkey / NFS 的等价判据是：

| 服务 | "配置对不对" | "服务可用吗" |
|---|---|---|
| MariaDB | `mysqld --validate-config`？或 `systemctl start` 后看日志 | 端口 3306 + `mysqladmin ping`（要装 client）/ 或 `ss` + `systemctl is-active` |
| Valkey | 无独立校验命令 | 端口 6379 + `valkey-cli PING`（返回 `PONG`） |
| NFS | `exportfs` 的解析 | ★ **`showmount -e 127.0.0.1` 能看到我们的导出**（这才是"导出真的生效"） |

★ 其中"让导出生效"这一步**已经查到答案**（见 §1.6）：`svc.restart nfs-server` 的 `ExecStartPre`
就是 `exportfs -r`，所以**大概率不用新增动作** —— 真机确认即可。

★ 这里会遇到一个**真实的设计问题**：`expect` 白名单只有 5 类（`present/absent/free_port/state/http_status`），
**"命令返回 PONG" 这类判据怎么表达？** 三条路：
  （a）扩 `expect` 白名单（走规范）
  （b）复用一个已有动作（如 `net.port` + `svc.list` 组合）
  （c）新增一个只读动作（如 `db.ping`）
→ **这是 T6 必须做的设计决断之一**，写在 §11 与 §12。

### 9.2 T6 预判的坑

| # | 预判的坑 | 预防 |
|---|---|---|
| 1 | ★ **`pkg.install mariadb-server` 会顺带装一堆依赖**（client / 库 / `mysql-selinux`），第二次跑的 `changed` 判定要准 | 用 T5 的 `pkg_install` 推导规则；实测"已装 → 不变" |
| 2 | ★ **数据库的"数据目录" `/var/lib/mysql` 是数据**：`keep_data` 必须保住它，`purge_paths` 才能删 | 照 Nginx 的 `{{ root_dir }}` 范式；★ **全靠实测验**（T5 的教训：承诺要真去验） |
| 3 | ★ **`valkey` 与 `redis` 的命令名不一样** | ✅ **已查清**（§1.6）：只有 `valkey-*`，**没有 `redis-*` 兼容名** → 健康检查用 `valkey-cli -p <port> PING`；`valkey-cli` 与 server **在同一个包**里，不用额外装 |
| 4 | ★★ **NFS 的"导出生效"** | ✅ **已查到答案**（§1.6）：`nfs-server.service` 的 `ExecStartPre` 就是 `exportfs -r` ⇒ **用 `svc.restart nfs-server`**，**不新增动作**。真机确认一次即可（写 exports.d → restart → `showmount -e` 看到） |
| 5 | ★ **NFS 端口不止 2049**（还有 20048 mountd、111 rpcbind） | 健康检查与端口白名单要按**整组**写，别只写 2049 |
| 6 | ★ **`file.remove` 的白名单不含 `/srv`** | ✅ **已定**：导出点用 **`/opt/aoc-nfs/<名字>`**（在 `^/opt/<名>` 里 ✓）；导出配置写 **`/etc/exports.d/aoc-<名字>.exports`**（在 `^/etc/<名>/...` 里 ✓）。**两条都在白名单内** → 全删删得掉 |
| 7 | ★ **MariaDB 首次启动会初始化数据目录（`/var/lib/mysql`），耗时较长** | ✅ 已查清：`mariadb-server` 的 rpm scriptlet **不建数据目录**（`dnf repoquery --scripts` 无相关输出）⇒ 初始化发生在**首次 `svc.start`** 时（由单元内部触发）。配方步骤要走合理超时，`svc.start` 之后**紧跟健康检查**（照 Nginx 的"真实失败暴露"姿势） |
| 7b | ★ **MariaDB 的"配置语法校验"命令**（要不要扩 `svc.configtest`） | ⏳ 真机实测 2 个候选：① `mariadbd --validate-config`（MySQL 8 有，MariaDB 10.11 **可能没有**）② `mariadbd --verbose --help`（会解析配置文件，语法错会报）。★ 都不行的话，**诚实的兜底是"MariaDB 配方不做配置预校验"并写明原因**，而不是拿 `svc.start` 当语法检查器 |
| 8 | ★ **SELinux = Permissive 不是 Disabled**：MariaDB 改路径可能留 AVC 记录 | 别把路径改到非常规位置；体检时 AVC 会红 → 要能解释 |
| 9 | ★ **多服务并存时的端口冲突** | 配方参数默认值要避开已知占用（Harbor 80/443 在 docker-01，但 docker-01 不参与） |
| 10 | ★ **内存 3.6G**：MariaDB 默认配置对小内存不友好（`innodb_buffer_pool_size`） | 模板里显式给小值（如 128M），并写进 `note` 说明为什么 |
| 11 | ★ **`svc.configtest` 扩枚举是"改平台"** | 先规范后代码；扩的时候**只加命令名、不加任意命令**（安全契约 §4）。★ 见 #7b：MariaDB 的校验命令**要真机验过**才敢写进枚举（写进去一个跑不通的命令 = 多一道假的闸门） |
| 12 | ★ **别把 `goharbor/valkey-photon` 当业务镜像用** | 它是 Harbor 自己的组件；误用等于拿生产部件的镜像做实验 |

#### ★ 白名单修订一（2026-09-26 · T6·S3 真跑时发现必须动一次）

| 项 | 原白名单 | 修订后 | 为什么必须改（**不是"顺手放宽"**） |
|---|---|---|---|
| Valkey 的配置文件 | `/etc/valkey/` | **加一条 `/etc/sysconfig/valkey`** | ★ valkey 包**没有**配置 drop-in 目录（`/etc/valkey/valkey.conf` 里的 `include` **全是注释**，实测）；而**平台没有 `daemon-reload` 能力**（全库动作无一处做它）⇒ "写自己的 conf ＋ systemd drop-in 覆盖 `ExecStart`"这条路**实测走不通**，而且会造成**假绿**（服务照样用包自带配置跑、健康检查全绿，我们的配置一个字没被读过）。**唯一可被证伪的写法**就是用它单元自己留的钩子：`EnvironmentFile=-/etc/sysconfig/valkey` ＋ `ExecStart=… $OPTIONS`；而那个文件**默认不存在**（实测）⇒ 是**纯自造**的，写得进、删得掉、全删也删得掉。★ 实测反证：把该文件里的 `OPTIONS` 写坏 → `valkey-server` **真的起不来**（`svc.restart` failed、探针 3/3 判红）。规范口径见 `docs/动作规范.md` §12.13.5 / 检查清单 51~52 |

## 附：T6 的一句话总结

> T5 交付的是"**一件能跑通的事**"，T6 要交付的是"**一条能重复的生产线**"。
> 而这一阶段真正的难点**不是"怎么装 MariaDB / Valkey / NFS"**（那各是几条命令），
> 而是三件事：
> **① 那张清单照着做第二遍、第三遍还对吗（引擎会不会露馅）**
> **② 服务类的"数据"与"配置"能不能在正反两个方向上都说清楚（`keep_data` 是承诺，要真去验）**
> **③ 遇到"环境不提供的东西"（mysql/redis 包名、公网镜像、非 systemd 的生效动作）怎么办**
> —— 把这三件做对，第三阶段（K8s / 监控）才有地基。
