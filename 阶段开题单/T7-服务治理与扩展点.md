## 3. 范围（做什么）

### 3.1 规范升 v1.8（S0，铁律：先规范后代码）

见 §11。**动 `app\` 核心代码之前**必须先补：装载期校验的"候选列表"语义、删除类步骤的"终态达成"语义、配方装载/重载的约定、配方批量的闸门规则。

### 3.2 主线 1 · 升级

1. **新增只读动作 `pkg.outdated`（升级预检）**：等价于 `dnf check-update` —— 列出"已装但仓库里有更新"的包（名字 / 当前版本 / 可用版本 / 仓库）。
   ★ **它是个只读动作、进域 H 账本**；★ **退出码 100 = 有更新、0 = 无更新**（这是个经典坑：**rc≠0 不等于失败**，与 `pkg.search` 里 `rpm -q` 的"rc = 缺几个包"同族，必须写进 `ok_exit_codes`）。
2. **"升级"在配方层怎么表达**（★ 待拍板，见 §10.2）：
   - 甲案：**不新增动作**，用"预检（只读）+ `pkg.update` + 重跑配方验幂等"三步组合；
   - 乙案：新增"配方级升级模式"（第四个按钮「升级 / 收敛」）。
   ★ 倾向**甲案**（少一个动作、少一套闸门），但必须把"**升级前后该怎么验**"写进文档。
3. ★ **升级后的幂等**：升级完**再跑一次配方必须零变更**（否则说明我们的 `changed` 判据把"包版本变了"误判成了"我们的配置变了"）。这是本主线的**关键验收**。
4. ★★ **把"回退"从一句话承诺，变成"能执行、能留证"的动作**（★ S0 起草时新核出的**欠账**）：
   现在 `pkg.install` / `pkg.update` / `pkg.remove` 的**结论模板里都写着**"回退：`dnf history undo <事务号>`"，
   但**平台没有任何动作能做这件事**（全库 48 个动作里没有）—— 换句话说：
   **我们承诺了一条"得让人自己 ssh 上去敲"的回退路径**。
   ⇒ 新增 **`pkg.rollback`（🔴 red · 按事务号回退）**：列事务 → 手输确认词 → `dnf history undo <ID>` → **自证**（版本真的回到"更新前"）。
   ★ 这与检查清单 47 / T6 那句"**承诺兑现不了比不承诺更坏**"是同一把尺子；
   ★ 它同时让 §10.3 #2 那笔"**从没真验过的账**"第一次**可以真跑验证**。

### 3.3 主线 2 · 卸载幂等（T6 遗留 #2）

1. **改"删除类步骤"的成败语义**：目标**本就不存在** ⇒ 视为**已达终态**（不是失败）。落点：`file.remove` / `pkg.remove` 的 `PRECHECK_FAILED`。★ **先升规范**（T6 已把口径写进 §12.6.5 的"删除类看终态"，这里是把**路径**那一半补齐）。
2. **加"终态收敛检查"**：全删模式除了判 `remove_packages` 的 `absent`，还要判 **`remove_config` / `purge_paths` 的路径不存在**（★ 需要一个**只读**的"路径存在性"采集源 —— 要么扩 `expect` 白名单（走规范），要么复用既有动作）。
3. **验收**：在"配置已删"、"目录已删"、"包已卸"三种**部分完成**的现状下，各点一次「全删」→ 三次都必须 ok 且终态一致。

### 3.4 主线 3 · 部署组回退（备份与恢复的"策略层"）

1. **"一次执行"成为一个可回退单元**：`recipe_runs` 已经记了 `checkpoints`（沿用了 T3 的备份机制）⇒ 在**配方执行详情**里给一个「回到这次部署前」的入口。
2. ★ **形态必须是"人在环 + 逐项 + 自证"**：
   - **不做自动回滚**（规范 §9.2 的边界）；
   - 恢复**逐项**列出（哪个文件 / 哪个目录 / 从哪个备份），每项要点一次或一次确认；
   - 恢复后**逐字节自证**（复用 T3/T5 的 sha256 比对 + 目录型恢复的"多套一层"修复）；
   - ★ **不可恢复的东西必须明说**（包？systemd 状态？服务重启？）—— "回退不到"比"以为回退了"好。
3. **顺带把 T6 遗留 #3 讲清**（参数变更留下的上一版产物）：至少在**界面与文档上明确**"上一次执行写过的路径不会被本次清理"，并把它作为**已知边界**写进规范（要不要真做清理，由 §10.2 拍板）。

### 3.5 主线 4 · 用户自写配方（扩展点）

1. ★ **配方热装载**：`/api/recipes/reload`（或启动时 + 显式重载两种）—— 让"写一份新配方"**不用重启控制台**。
   ★ 但**必须先过装载期校验**：不合规**不装载**，并把**哪一行/哪个键错**说清楚（现有校验已经很强，缺的是"出口"）。
2. **配方脚手架**：`tools\new-recipe.py <id>`（零依赖）—— 从样例生成一份**能通过装载校验**的骨架 + 模板占位 + TODO 注释。
3. **配方体检**：把"装载期校验"做成一个**可单独跑的只读检查**（`python tools\recipe-check.py <file>` 或界面上一个按钮），输出**人话**的错误清单。

### 3.6 （薄）配方批量

## 9. 技术要点与坑

### 9.1 继承下来的（**不许再犯**）

| # | 要点 |
|---|---|
| 1 | ★★ **"命令返回 0" ≠ "事情成了"** —— 删除类操作看**终态**（§12.6.5）；报告只念**真做了**的（§12.6.4） |
| 2 | ★★ **判据必须可被证伪** —— 写坏了不红的写法一律不用（§12.13.5） |
| 3 | ★★ **代码 diff 不算验收证据** —— T6 最贵的一次抓获就是"修复只改了 4 条出口里的 3 条"（检查清单 50 / 断言 ⑱） |
| 4 | ★ **同一字段的每个出口都要改**（上一条的根源） |
| 5 | ★ **配置要写在"服务自己留的钩子"上**，且**永远不写包自带的主配置**（§12.13.1 / §12.13.5） |
| 6 | ★ **拿"服务活着"当"配置生效"是假绿** —— 判据要让**配置本身**参与（§12.13.5） |
| 7 | ★ **模板里没有"注释"** —— 说明文字里的裸 `{{ }}` 照样被当占位符（§12.4） |
| 8 | ★ **建目录靠"往目录里写文件"**；**目录必须先于"配置生效"存在**（§12.13.6） |
| 9 | ★ **端口按整组钉，且以真机实际监听为准**（§12.13.6） |
| 10 | ★ **数字必须从账本实时算**（`GET /api/coverage`），手算过一次就错过一次（T6 教训第 6 条） |
| 11 | ★ **取证也要按正确顺序**（"先还原完再拍快照"，T6 踩过：拍到了中间态然后去怀疑别的东西） |
| 12 | ★ **改了 `app\` 先补规范、先重启服务**；新增"能变更"的动作**必须**登记 `changed` 推导规则 |

### 9.2 T7 预判的坑

| # | 预判的坑 | 预防 |
|---|---|---|
| 1 | ★★ **`dnf check-update` 的退出码**：有更新返 **100**、无更新返 **0** —— 把 100 当失败会让"有更新"这件事永远报错 | `ok_exit_codes: [0, 100]`；★ 并把"rc 的语义"写进动作 `note`（与 `rpm -q` 的"rc = 缺几个包"同族） |
| 2 | ★ **`pkg.outdated` 在源失效的机器上会给出误导性结论**（docker-01） | 源不可达 ⇒ 判"**无法判定**"，**不许**报"没有可升级的"（§10.6.3「空结果 ≠ 空数据」） |
| 3 | ★ **升级会动依赖**：升 A 可能连带升/降 B（`dnf` 的事务是一次性的） | 报告里必须给**事务号**与"本次动了哪些包"；★ 验收要包含"**升级后重跑配方零变更**" |
| 4 | ★ **热装载与"正在执行的配方"打架**：重载时如果有配方正在跑 | 重载**只换新执行的快照**，正在跑的那次继续用旧定义；★ 写进规范 |
| 5 | ★ **热装载可能把"半个坏配方"带进来**：校验不过就不装载 | 装载期校验是**整体**的（一份坏 → 不装载并说清哪份/哪一行）；★ 且**不许**因此让已装载的配方失效 |
| 6 | ★ **"路径不存在"这种判据**：`expect` 现在没有"文件不存在"这一类 | 要么扩白名单（走规范），要么复用既有只读动作；★ **不许**在配方里就地发明 |
| 7 | ★ **部署组回退会牵动"不可恢复的东西"**：包升级、systemd 状态、服务重启后的内存态 | 报告**逐项标注"能回去 / 回不去"**；★ 宁可少承诺，也不要让人以为"整机都回去了" |
| 8 | ★ **配方批量的闸门**：红档禁止批量是 T3 硬规矩 | 沿用；★ 且"批量"必须是平台能力，**动作/配方 YAML 里不许声明"我要批量"**（§9.3 的老规矩） |
| 9 | ★ **批量下的幂等**：两台机器可能不在同一现状（一台装过、一台没装） | 验收分开写："**同现状两台**各跑两次→都零变更"；"**不同现状**"属多机治理，见 §4 不做什么 |
| 10 | ★ **别把"缺 2 项 T3 缺口"当 T7 的义务** | 它是"顺手且划算"，不是本话题的命题；做不做由 §10.2 拍板，**不许**挤掉四条主线 |

## 附：T7 的一句话总结

> T5 交付了"**一件事能整体交给它**"，T6 交付了"**这条产线能重复**"。
> T7 要交付的是"**装上去之后，怎么安全地动它**"：
> **升级先知后动、卸载不挑现状、整组回退有人把关、别人也能照着样例加服务。**
> ★ 这一阶段真正难的仍然不是"怎么写升级"，而是三件事：
> **① 判据要能被证伪 ② 报告只许念真做了的 ③ 承诺了就要真去验**（T7 §10.3 #2 就是一笔记了很久的账）。
