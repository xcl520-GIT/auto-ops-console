## 0. 一句话

> T1~T4 证明了**能看 / 能加 / 能改 / 像产品**。
> T5 要证明的是：**"把一件运维的事"整体交给它** ——

### 0.1 ★ 三条设计宪法（本话题的"宪法"，违反即返工）

| # | 宪法 | 一句话 |
|---|---|---|
| **1** | **配方只声明「要什么」，不声明「怎么判断」** | 判定与分支一律走平台侧。理由与 T4 的 `checkup` 完全一致（**采集走动作、判定走平台**）。一旦允许在 YAML 里写比较逻辑/阈值/表达式，配方就会变成**第二套程序** —— 不可校验、不可解释、出问题没法定位 |
| **2** | ★ **"没变"必须可断言** | 设计要求"重复部署 = 第二次零变更"，但现有 42 个动作只回答"**成功了吗**"，**没有统一的「变了没有」**。→ 平台统一采集 `changed`，汇总成"**本次变更清单**"，**验收 = 第二次这张清单为空** |
| **3** | **每个正向步骤都要有反向操作** | 停止 / 卸载·**保留数据** / 卸载·**全删**——三个按钮都必须真跑过 |

## 2. 目标（四条主线）

### 主线 1：**Recipe（配方）引擎** —— 第二阶段的地基

一个配方 = **一份磁盘上的 YAML**（可读、可改、用户能照着样例自己加），
声明：**参数 → 前置检查 → 步骤（引用现有 Action）→ 期望 → 健康检查 → 检查点 → 反向操作**。

★ **不允许写进 YAML 的东西**（宪法 1 的落地）：

| ✅ 允许写进 YAML | ❌ 不许写进 YAML |
|---|---|
| `expect: { state: { unit: nginx, equals: active } }`（**期望**） | `expect: "state == 'active' && uptime > 30"`（**表达式**） |
| `expect: { http_status: { url: "...", equals: 200 } }` | 自定义脚本 / 内联 shell |
| `notify: [重启 Nginx]`（**声明"什么变了要做什么"**） | `if ... then ... else`（分支） |
| `when: "{{ enable_ssl }}"`（**单值开关**，复用现有 `run` 元素的 `when` 语义） | 循环 / 计算 / 函数调用 |

### 主线 2：**幂等与"变更清单"** —— 让"第二次零变更"可断言 ★ 最硬的一根骨头

见 §3.4。核心：**平台统一采集 `changed` → 汇总成"本次变更清单" → 幂等的验收就是断言这张清单为空**。

### 主线 3：**首个服务 · Nginx 部署闭环**（端到端，一次点击）

```
预检（端口没被占 / 没装过） → 装包 → 渲染配置写盘 → 配置语法校验（nginx -t）
   → 启动 + 开机自启 → 健康检查（HTTP 200） → 出报告（含"本次变更清单"）
```

**反向操作**（★ 设计要求：只写正向的配方不合格）：

| 按钮 | 做什么 |
|---|---|
| **停止服务** | 停 nginx（保留配置与数据） |
| **卸载 · 保留数据** | 停服 + 禁用自启 + 删配置，**保留**站点目录与日志 |
| **卸载 · 全删** | 上面全部 **+ 删站点目录与日志 + 卸包**（🔴 `red`，手输确认词） |
| **备份 / 恢复** | 复用既有护栏（改动前双份备份 + 一键恢复 + sha256 逐字节自证） |

### 主线 4：**检查点与"回滚指引"**（不做自动回滚，沿用既有结论）

- 配方执行过程中**自动登记检查点**（每个"变更步骤"前的备份记录 + 包事务号）
- 失败时：**不自动回滚**，而是给"**回滚到哪个检查点 + 一键恢复按钮 + 需要人工确认的原因**"
- 理由与 T3/T4 一致：自动还原可能把"其实没坏"的现场也覆盖掉

## 3. 范围（做什么）

### 3.1 配方 schema（新目录：`catalog/recipes/*.yaml`）

```yaml
id: nginx
name: Nginx
version: "1.24"              # 版本锁定（装哪个包 / 用哪份模板）；★ 不许写查不到的版本号自欺
summary: 一键部署 Nginx（配置模板 + 健康检查 + 可回滚 + 可卸载）
risk: yellow                 # 配方整体风险（取步骤内最严）

params:                      # ★ 复用现有 params 机制（label/type/pattern/default/help/min/max/choices）
  - { name: port,        label: 监听端口,     type: int, default: 8080, min: 1, max: 65535 }
  - { name: server_name, label: 域名,        type: str, default: "_" }
  - { name: root_dir,    label: 站点目录,     type: str, default: "/var/www/aoc-nginx" }
  - { name: worker,      label: worker 进程数, type: int, default: 2, min: 1, max: 16 }

preflight:                   # 不成立就中止（别改坏）
  - expect: { absent:   { action: pkg.installed, args: { package: nginx } } }
  - expect: { free_port: "{{ port }}" }

steps:
  - name: 安装
    action: pkg.install
    args: { package: nginx }

  - name: 渲染配置
    template: tpl/nginx.conf       # ★ 模板文件放 catalog/templates/（不引 Jinja2，见 §3.3）
    dest: /etc/nginx/nginx.conf
    notify: [重启 Nginx]           # ★ 只有"内容真的变了"才触发（靠 changed）

  - name: 配置语法校验
    action: svc.configtest         # ← 新增动作（可配置的校验命令，如 nginx -t）
    args: { unit: nginx }

  - name: 启动并自启
    action: svc.start
    args: { unit: nginx }
  - action: svc.enable
    args: { unit: nginx }

  - name: 重启 Nginx               # ★ 被 notify 触发的步骤
    action: svc.restart
    args: { unit: nginx }
    trigger_only: true             # ★ 只能被 notify 唤起，跑配方时不会无条件执行

health:
  - expect: { http_status: { url: "http://127.0.0.1:{{ port }}/", equals: 200 } }

uninstall:
  stop:    [ { action: svc.stop,    args: { unit: nginx } } ]
  disable: [ { action: svc.disable, args: { unit: nginx } } ]
  purge_paths: [ "/etc/nginx", "{{ root_dir }}" ]     # ★ red + 路径白名单（§3.6）
  keep_data:   [ "{{ root_dir }}", "/var/log/nginx" ] # "保留数据"时**不删**的东西
```

> ★ 注意：上面每一处判定都写成了**期望**（`expect`），**没有一处表达式** —— 这就是宪法 1。

### 3.2 参数表单（复用现有机制，零新前端框架）

- 由 `params` 自动生成（现有 `catalog.py` 的表单渲染已在做这件事）
- 新增：**配方级的分组与顺序**（5~8 个填空题，别一屏 20 个）
- 新增：**必填校验 + 越界提示**（`min`/`max`/`pattern` 已有，沿用）

### 3.3 ★ 模板渲染（结论已定：**不引入 Jinja2**）

**扩展项目已有的 `{{ }}` 约定，纯替换、零逻辑。**

| 项 | 做法 |
|---|---|
| 模板位置 | `repo\catalog\templates\<service>\*.conf`（进 Git，可读可改） |
| 占位符 | `{{ 参数名 }}`（与 `render_argv_element` **同一套约定**，**不造第二套**） |
| 允许的能力 | 变量替换 + **必填校验**（缺必填 → **报错中止**，**绝不静默写成空值**） |
| **禁止的能力** | ❌ 条件 ❌ 循环 ❌ 表达式 ❌ 函数调用 ❌ 内联脚本 |
| 字面量转义 | 模板里要写真的 `{{` → 用 `{{ '{{' }}`（**本话题定死这一个语法并写进规范**）；nginx 自身的 `$var` 不受影响 |
| 写盘方式 | 复用 `write_file` 的搬运实现（base64 + `chmod`）；★ **先比对 sha256，相同则不写**（幂等来源） |
| 渲染产物留证 | **渲染后的最终内容要存档**（可回放："当时写进去的到底是哪一份"） |

### 3.4 ★ 幂等与变更清单（宪法 2 的落地）

**问题**：设计要求"重复部署 = 第二次零变更"，但现有动作只回答"成功了吗"。

**做法（三层，都不需要改造那 42 个动作）**：

**① 平台统一采集 `changed`** —— 从**已有的前后对照**推：

| 动作类别 | `changed` 怎么推 | 依据 |
|---|---|---|
| `pkg.install` / `pkg.remove` / `pkg.update` | `before` 的存在性/版本 vs `after` | 动作自带 before/after 步骤 |
| `svc.start/stop/enable/disable` | `before` 与 `after` 的**状态字段不同** | 自带 before/after |
| `svc.restart` | 用**启动时间戳变化**判定（不是恒为 true） | 动作已有"时间戳自证" |
| `write_file` / **模板渲染** | **渲染内容 sha256** vs **目标机现有文件 sha256** | 需新增"先比对再写" |
| `file.push` | 上传前后 sha256 | 已有双向校验 |
| `cron.upsert` / `cron.remove` | 目标文件 sha256 变化 | 走 `write_file` 通道 |
| `fw.port-open` / `fw.port-close` | 规则查询前后对比 | 已有自证 |
| 只读动作 | 恒 `false` | — |
| ★ **未知来源** | **`unknown`** —— **在报告里显式标出**，**不许默认 false** | 防"看起来没变" |

**② 汇总成"本次变更清单"**（`changed_steps`），结论里**显式列出**：

```
本次变更：2 项（渲染配置 / 重启 Nginx）｜ 未变更：5 项 ｜ 无法判定：0 项
```

**③ ★ 幂等的验收方式就是断言这张清单为空** —— 第二次跑同一配方，`changed_steps` 必须是 `[]`。

> 好处：**可断言**（不是"看起来没变"）、**复用既有能力**、而且顺带带来产品级价值：**"这次跑到底改了什么"一眼可见**。

### 3.5 检查点、健康检查与失败处置

| 能力 | 做法 |
|---|---|
| 检查点 | 每个变更步骤前自动登记（复用既有备份 + 包事务号）；报告里列出"可回滚到的点" |
| 健康检查 | 配方末尾 `health` 段，**期望类型白名单**；**不过 = 配方判 failed** |
| 失败处置 | ❌ 不自动回滚；✅ 给"回滚到哪个检查点 + 一键恢复" + "先去看哪一步的原始输出" |
| 部分失败 | 沿用批量规则：**失败即中止**（后续步骤不跑），但**已完成步骤的留证与检查点都保留** |

### 3.6 需要新增的动作（配方缺的那几只手）

| 新动作 | 用途 | 风险 | 约束 |
|---|---|---|---|
| `svc.configtest` | 配置语法校验（`nginx -t` / `sshd -t` 之类**可配置**的校验命令） | green | 现有动作里**没有**"校验配置但不改状态"的动作；★ 命令须先判存在（缺工具 → ⚠️ 无法判定，沿用 `checkup` 的降级姿势） |
| `file.remove` | 卸载**全删**（受限路径） | 🔴 **red** | ★ **路径白名单**：只允许 `/etc/<name>`、`/var/lib/<name>`、`/var/log/<name>`、`/opt/<name>`、`/var/www/<name>` 形式；**拒绝** `/`、`/etc`、`/usr`、`/var` 及其直接子目录；**拒绝 `..`**；**白名单校验必须在路径规范化之后做**；**禁止批量** |

> ★ 另有一个"形式选择"：模板渲染做成**步骤类型**（`template:` + `dest:`，推荐）还是独立动作（`tpl.render`）。
> **开工时定**，不影响其它设计。

## 7. 验收标准（逐条可对照）

| # | 标准 | 判定方式 |
|---|---|---|
| 1 | ★ **一次点击：从"没装"到"Nginx 可用"** | 填 4~8 个参数 → 跑完 → 健康检查 HTTP 200；全程不碰终端 |
| 2 | ★★ **幂等：重复跑第二次零变更** | 再跑一遍 → 报告里 **`changed_steps` 为空**；受管文件 sha256 前后一致 |
| 3 | **参数表单可用且友好** | 只面对 5~8 个填空题；越界输入有明确提示；**必填缺失报错而不是写空值** |
| 4 | ★ **反向操作齐备**（设计要求：只写正向不合格） | 停止 / 卸载·**保留数据** / 卸载·**全删** 三个按钮都真跑过，且"保留数据"确实**没删**站点目录 |
| 5 | **检查点与回滚指引** | 故意让某步失败 → 报告给出"回滚到哪个点 + 一键恢复"；恢复后 sha256 逐字节自证 |
| 6 | **健康检查真的会失败** | 故意写个非法配置 → `svc.configtest` 拦住 / 健康检查判红，**不许"看似成功"** |
| 7 | ★ **"声明式"没被破坏** | 配方 YAML 里**没有一处**表达式/脚本/分支（**自检要能断言**，见 §12） |
| 8 | ★ **加服务只写 YAML + 模板** | 新增一个**假配方**（指向已有动作）**不改 `app\` 代码**即可装载；并产出一张"新增一个服务需要做什么"的清单 |
| 9 | **全量自检不回退且新增** | ≥ **168**（T4 基线）并新增配方相关检查项；离线层仍可跑 |
| 10 | **靶子纪律 + 系统零改动** | 三台 K8s 与 Harbor 只读；变更只在 `aoc-` 对象 + `nginx` 包 |
| 11 | **交接三件齐** | 继续工作（覆盖式）+ T5 结题回执 + 总纲 §3 勾选 |
| 12 | ★ **账本已回填** | 新动作与"服务目录"能力出现在覆盖率页；**`platform:` 段的 `done` 布尔必须同步更新**（T4 的教训） |

## 8. 技术要点与坑

### 8.1 从 T4 继承的（不许再犯）

| # | 要点 |
|---|---|
| 1 | ★ **`Api` 方法存在 ≠ 接口可用**：新增接口**必须同时登记 `dispatch`**（规范 §9.9） |
| 2 | ★ **验证要在"界面真正走的那一层"（HTTP）**，别只验底层函数 |
| 3 | ★ **改完代码先重启服务再验证**（旧进程占 8787 会让你误判） |
| 4 | ★ **交付一个新能力时必须同时回填账本**（`entries` 自动对账，但 `platform:` 段是**显式布尔**） |
| 5 | ★ **"某物不存在"必须由退出码承担**，不能写成 verify 的非空断言（§9.6） |
| 6 | **YAML 标量里出现 `: ` 要加引号；`run` 元素含逗号要加引号**（§9.7 / §9.8） |
| 7 | **改项目文件只用 `writeFile` / `editFile`；同一文件每批只发一个编辑** |
| 8 | **脚本能跑 ≠ 界面能跑**：`tools\*.py` 直连 engine，必须另做 HTTP 层验证 |

### 8.2 T5 新增的坑（预判）

| # | 预判的坑 | 预防 |
|---|---|---|
| 1 | ★ **`changed` 采集口径不统一** → 幂等证明变成"看起来没变" | 统一在引擎一处采集；**每种动作写明推导规则**（§3.4）；未知来源一律 `unknown` 并**在报告里显式标出**（**不许默认 false**） |
| 2 | ★ **模板里静默写成空值** → 配置语法错，界面却显示成功 | 必填参数缺失**必须报错中止**；**渲染产物要存档** |
| 3 | **`notify` 引发"改了就重启"的抖动** | 只有 `changed=true` 才触发；`trigger_only: true` 的步骤**在计划预览里要单独列出**（不能让人以为它会无条件跑） |
| 4 | **配方 YAML 里写进了逻辑** | 自检断言：配方 schema **只允许白名单键**；出现 `expr`/`if`/`script`/`eval` 之类 → **红** |
| 5 | **`file.remove` 路径白名单被绕过**（`/etc/nginx/../../`） | 白名单校验**在路径规范化之后**做；拒绝 `..`；拒绝根目录与其直接子目录 |
| 6 | ★ **T16 的"等条件成立"要留钩子**：将来会有"开机 → 等 SSH 就绪"这类**等待类步骤** | 本话题**不实现**，但步骤模型要预留一类 `wait`/`expect` 式步骤，**避免 T16 时重写引擎** |
| 7 | **配方版本与包版本漂移**（`version: "1.24"` 指向的包没了） | 版本字段**要么能定位**（`dnf` 查得到），**要么明确写"不锁定"** —— 不许写个查不到的版本号自欺 |
| 8 | **`svc.configtest` 在没装 nginx 时命令不存在** | 先判命令存在（缺工具 → ⚠️ 无法判定，沿用 `checkup` 降级姿势） |
| 9 | **幂等误判**：日志/时间戳每次都在变 | 比对口径**只看受管文件 sha256 与状态字段**，**不要把日志内容算进去**（与批量 diff 口径同源，§9.3） |
| 10 | **`nginx` 装了却起不来**（端口占用 / 配置引用了不存在的目录） | `preflight` 先查端口；`root_dir` 由配方**主动创建**（别假设它存在） |

## 12. ★ 自检要新增哪些断言（S1~S4 的验收依据）

| # | 断言 | 为什么 |
|---|---|---|
| 1 | **配方 YAML 只含白名单键**（出现 `expr`/`if`/`script`/`eval` → 红） | 宪法 1 的机器化看门狗 |

| 3 | **配方引用的 `action` id 都存在**，参数名都对得上 | 防"配方写得像真的，一跑就 400" |
| 4 | ★ **每个配方都有 `uninstall` 段且含"保留数据 / 全删"区分** | 宪法 3（"只写正向不合格"） |
| 5 | ★ **每种"能变更"的动作都有明确的 `changed` 推导规则**（漏了 → 红） | 宪法 2；防口径不统一 |
| 6 | **模板缺必填参数必须抛错**（正/负例各一条） | 防静默空值 |
| 7 | **`file.remove` 路径白名单负例**（`..` / `/` / `/etc` → 必须被拒） | 破坏性动作的边界 |
| 8 | **假配方跑两次 `changed_steps` 为空**（离线可验） | 幂等的离线回归 |
| 9 | **路由对账**（沿用 T3 那条）：`app.js` 请求的每个 `/api` 路径都要被 `dispatch` 认领 | §9.9 |
| 10 | **`platform:` 段 `done` 布尔与事实一致** | T4 §10.3.4 那个坑的看门狗 |

## 附：T5 的一句话总结

> T1 能看 → T2 能加 → T3 能改 → T4 像个产品 → **T5 把"一件完整的事"交出去**。
>
> 而这一阶段真正的难点**不是"怎么装 Nginx"**（那只是 5 条命令），
> 而是三件设计上的硬骨头：**① 判定不许进 YAML ② "没变"必须可断言 ③ 每个正向步骤都要有反向操作**。
> 把这三件做对，T6 的 Docker / MySQL / Redis 就只是"再写几份 YAML 和模板"。
