## 3. **不做什么**（划清边界，防止范围失控）

1. ❌ **不做新功能、不加动作、不改配方** —— T11 是交付话题，**一行平台代码都不改**。
   若发现缺陷：**只记录、只标注，不顺手修**（要修须用户单独拍板 —— 与 T9/T10 的"修一类不修一处"不冲突，那是修缺陷的话题的纪律）
2. ❌ **不擅自改仓库可见性、不擅自建公开仓库**（**红线 4**）—— 脱敏与切换公开**由用户显式发起**，本话题**只做"公开化的准备物"**，仓库全程私有
3. ❌ **不做脱敏**（`192.0.2.x` 主机名/IP、真实命令输出、`hosts.yaml` 真实拓扑）——
   ★ 依据用户拍板：本话题**不切公开**，脱敏另立一步；因此新建的公开面向文件里**照实写内网事实**，
   但**在文首显式写明"公开前必须脱敏"**（不许留下一个"以为已经脱敏了"的错觉）
4. ❌ **不做简历素材与讲述稿**（用户拍板：等公开化那一步再写）
5. ❌ **不动靶机**：K8s 集群（三节点 Ready）与监控栈（`node-03` 上五单元）**现在都活着** ——
   只允许**只读取数**；截图重跑只走**只读路径**，**不重跑任何变更**（变更链路引用 T5/T6/T7 的既有真跑证据）
6. ❌ **不把截图当"机器可核证据"** —— `repo\README.md` 现有那句"仓库里不放截图"的立场**要重新表述**：
   截图**进入交付物**，但**必须与文字快照成对**，且**不给它独立结论权**
7. ❌ **不重写规范正文**：本话题只**新增** §13（交付与公开化），**不改** v1.13 任何既有条款
8. ❌ **不上 PDF / 不建站点 / 不做视频**（标准只要求 md ＋ 截图）
9. ❌ **不为了"数字好看"改口径**（覆盖率分母、自检条数一律不得因本话题调整）

## 9. 技术要点与坑

### 9.1 继承下来的（★ **不许再犯**）

1. ★★ **"报告说假话"有四个方向**（T9 立、T10 重犯）：**假红** · **假变更** · **假警报** · **自相矛盾**。
   → 本话题的等价物是 **"交付物说假话"**：**数字过期**（README 停在 T0）· **断言无出处** · **路径点不开** · **说法与环境不符**。
   ★ 本话题要把它**变成四条可扫的断言**（验收 #2 #5 #12 #13）
2. ★★ **"一个缺陷只有一处"是错觉**（T10 ⑫）：改一个数时，先问「**这是这一处的毛病，还是这一类的毛病？**」 ——
   ★ 本项目就有一类现成的：**同一个数字写在 4 个地方**（根 README / repo README / 演示手册 / 证据索引）。
   → 处置：**一处定义（账本）、其余全部"从账本实时算"或引用**，不许各写各的
3. ★ **看门狗自己也会咬错人**（T10 ⑬）：★ 措辞扫描器第一版一定会有误伤 ——
   **匹配前先剥掉不该扫的东西**（`开发记录\` 内部文件、代码块里的示例），**豁免必须写明理由**
4. ★★ **离线绿 ≠ 完整绿**（T9 §12.52）：两道门都要跑，不许只跑离线
5. ★ **YAML 脚枪**（T10 ⑩ `": "` 与 `"`）：本话题写的是 **Markdown**，风险低 ——
   但**目录/表格里嵌 `: ` 与引号仍要留意**；★ 改完立刻喂装载自检
6. ★ **改写公开历史必须先征得用户同意**（标准 §7.7）—— ★ 本话题**不重写历史**

### 9.2 T11 预判的坑（★ 开工后逐条盯着）

1. ★★★ **手抄数字**（本话题最大的坑）：文档里的数字**必须实算**；
   ★★ 且**写完要再算一遍复核** —— "写完不复核"本身就是**新的假话来源**

3. ★★ **截图不可核**：所以**图必须配文字快照**（T10·S8 的做法：DOM 原文逐字可对）
4. ★ **改 README 时会造出"两个真相"**：根 README 与 `repo\README.md` 天然会写同一批数字

6. ★ **LICENSE 是法律决定** ⇒ 不代选（§10.2 #5）
7. ★ **不要顺手改代码**：本话题若撞见缺陷（例：文档里引用的路径已失效、`/api/...` 文案问题），

8. ★★ **公开化标准 §8 的反例清单**是硬约束：**堆形容词而无数值** · **只展示成功方案** ·
   **把 AI 藏起来或说成独立完成** · **数字没有版本与样本量** —— ★ 逐条对照，命中即改
