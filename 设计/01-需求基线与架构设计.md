## 1. 一句话定位

**一个跑在管理机上的本地 Web 控制台，把「Linux 主机纳管 → 基线收敛 → K8s 部署 → 监控告警 → 网络与排障」串成一条可点、可复现、留证据的流水线。**

它解决的问题不是「省几次手敲命令」，而是三件事：

1. **收敛**：机器状态从「我记得配过」变成「代码里写着，随时能重跑」；
2. **可见**：每一步动作、每一个采集值都能追到原始输出；
3. **可讲**：整套东西的取舍与踩坑过程能变成简历与面试的素材。

### 2.1 由基线推导出的隐含约束

| # | 推导结论 | 依据 |
|---|---|---|
| C1 | 控制台必须**零外部依赖或最小依赖**部署在管理机上 —— 管理机只有 4GB 内存，装不下重型运行时 | R4 + R7 |
| C2 | 监控栈**不能放进 k8s 集群里**，否则「监控与被监控同命」，且无法覆盖非 k8s 主机 | R3 |
| C3 | 采集体系必须支持**非 k8s 目标的静态注册**（手工加机器、加自定义 exporter） | R3 |
| C4 | 所有变更动作必须**幂等**（可重复执行、第二次零变更），否则 4 台机器反复调试必然漂移 | R4 |
| C5 | 必须处理**克隆/快照后的身份重复**（machine-id、SSH host key、IP、UUID） | R5 + R6 |

## 3. 边界：做什么 / 不做什么

### 3.1 做

- 主机**纳管**：资产清单、连通性探测、SSH 免密通道建立与健康检查
- **基线收敛**：时间同步(chrony)、SELinux、firewalld、软件源、内核参数、基础包、SSH 加固
- **部署流水线**：Rocky → 容器运行时 → kubeadm 集群 → 网络插件 → 存储 → 监控接入（R2）
- **监控告警**：exporter 安装注册、scrape 配置生成、告警规则管理、通知渠道（含通用 Webhook）
- **网络配置与排障**：`nmcli` 配置、DNS/网关校验、路由与连通性探测、端口探测、链路诊断、抓包辅助
- **一键体检（doctor）**：把「运维第一反应要敲的那几十条命令」固化成可复现的检查项
- **任务编排与审计**：每次执行落库、原始输出留档、可回放

### 3.2 不做（明确划掉，避免范围失控）

| 不做 | 原因 |
|---|---|
| 改造宿主机虚拟网络（vmnet / NAT 规则 / 虚拟网络编辑器） | 那是 VMware 的职责域，软件最多**只读感知** |
| 自动从零创建虚拟机 | R5 已定；收益远小于成本（见 §10.1） |
| 自己实现时序数据库 | 指标存储是专门问题，交给 Prometheus |
| 自己做可视化大屏 | Grafana 已经做得更好，自研等于浪费工期 |
| 多租户、RBAC、公网暴露、HTTPS 证书体系 | 本机单用户实验环境，做了也没人用（**这条要提前想好面试怎么答**） |
| 生产级高可用（控制台自身 HA / 集群化） | 单机实验台，超出规模 |

## 4. 环境规格

### 4.1 主机规划（4 台，用满上限）

| 主机名 | 角色 | 系统 | vCPU | 内存 | 磁盘 | 网络 | 承载服务 |
|---|---|---|---|---|---|---|---|
| `ops-mgr` | 管理机 / 监控中枢 | RHEL 10.x | 2 | 4 GB | 200 GB | NAT | 控制台本体、Prometheus、Alertmanager、Grafana、SQLite |
| `k8s-node1` | K8s 控制面 + 工作节点 | Rocky 10.x | 2 | 4 GB | 200 GB | NAT | kube-apiserver / etcd / containerd / kubelet |
| `k8s-node2` | 同上 | Rocky 10.x | 2 | 4 GB | 200 GB | NAT | 同上 |
| `k8s-node3` | 同上 | Rocky 10.x | 2 | 4 GB | 200 GB | NAT | 同上 |

> **合计虚拟资源**：8 vCPU / 16 GB / 800 GB（精简置备）。宿主机建议 ≥ 8 核 / 24 GB 内存 / 200 GB 可用空间。

**降级备选**（若宿主机内存吃紧或 k8s 内存不够）：改成 **1 台控制面 + 2 台工作节点**，把第 4 台留给第二个发行版做「纳管能力验证」。代价：控制面 HA 的证据链变弱。

### 4.2 VMware Workstation Pro 侧的设置要点

| 项 | 建议 | 理由 |
|---|---|---|
| 硬件兼容性 | 与 Workstation 版本一致（不要降到老版本） | 避免 API/vmcli 能力被旧兼容级别限制 |
| 磁盘置备 | **精简置备（thin）**，单盘 200 GB | 不一次性吃掉物理盘，但要记得定期 compact |
| 网络适配器 | NAT（默认即可） | R6 已定 |
| VMware Tools / open-vm-tools | 装 `open-vm-tools` + `open-vm-tools-desktop`（不需要桌面就只装前者） | 时间同步、关机信号、IP 上报 |
| 快照策略 | 每次「环境就绪」后打一个基线快照 | 后面所有实验都能回到干净点，是本项目最重要的成本控制手段 |
| 克隆时 | **必须重置身份**（见 §9.6） | 否则 machine-id / host key / IP 冲突，SSH 会拒连 |

### 4.3 管理通道（NAT 下能不能连通？）

**能，且不需要端口映射。** 原理：宿主机自带一张 `VMnet8` 虚拟网卡，NAT 网段的**网关和 DHCP 服务都长在宿主机上**，guest 与宿主机同处一个网段 —— 所以：

- **宿主机 → guest**：直达，直接用 guest IP 即可（`ssh ops-mgr`）✅
- **guest → 外网**：经宿主机 NAT 出去 ✅
- **guest → guest**：同网段二层可达 ✅
- **其它物理机 → guest**：❌ 不可达，需要 **NAT 端口转发**（本项目不需要，但设计上要知道这个边界）

> 这也是「NAT 不影响纳管」的底气所在。真正的风险不是连通性，而是**克隆/快照后 IP 冲突**。

## 5. 架构设计

### 5.1 分层

```
┌───────────────────────────────────────────────────────────────┐
│  L1  表现层   浏览器界面（原生 HTML/CSS/JS）                    │
│      · 资产总览 · 任务流 · 监控面板跳转 · 体检报告 · 审计日志   │
│      · 任务日志走 SSE 流式推送（长任务不能靠轮询硬等）           │
└───────────────────────────┬───────────────────────────────────┘
                            │  HTTP / JSON + SSE
┌───────────────────────────▼───────────────────────────────────┐
│  L2  接口层   本地 HTTP 服务（仅监听 127.0.0.1 / 内网）          │
│      · 路由与参数校验 · 任务创建/查询 · 事件推送 · 静态资源      │
└───────────────────────────┬───────────────────────────────────┘
┌───────────────────────────▼───────────────────────────────────┐
│  L3  领域层   7 个功能域（彼此只通过接口调用，互不 import 实现）  │
│      inventory │ baseline │ deployer │ monitoring │ net │       │
│      diagnose  │ task/audit                                   │
└───────────────────────────┬───────────────────────────────────┘
┌───────────────────────────▼───────────────────────────────────┐
│  L4  执行层   可插拔后端（同一套剧本，三种执行方式）             │
│      · HostProvider  : workstation | static-inventory | 未来 vCenter │
│      · Transport     : ssh（系统二进制 + 密钥，不需第三方库）     │
│      · Executor      : ansible-backend | shell-backend          │
│      · 采集扩展点     : exporter 注册表（node / windows / snmp / 自定义脚本）│
└───────────────────────────┬───────────────────────────────────┘
┌───────────────────────────▼───────────────────────────────────┐
│  L5  数据层   SQLite（inventory / 任务 / 审计 / 体检结果）        │
│      指标时序 → 交给 Prometheus（本项目不自己造 TSDB）           │
└───────────────────────────────────────────────────────────────┘
```

**三条架构红线**：

1. **领域层不直接执行命令** —— 所有变更经过执行层，才能统一做幂等、超时、审计、回滚点。
2. **采集与存储分离** —— 软件只负责「装 exporter + 生成 scrape 配置 + 管告警规则」，**不解析、不存储指标**。
3. **一切外部能力走接口** —— VM 来源、传输方式、执行后端、采集器全部可替换，换一家的代价是写一个 adapter，不是改全栈。

### 5.2 功能域清单

| 域 | 职责 | 关键能力 | 验收点 |
|---|---|---|---|
| `inventory` | 资产清单与连通性 | 增删改查、SSH 通道自检、系统指纹识别（发行版/版本/内核） | 4 台全部纳管，指纹识别正确 |
| `baseline` | 基线配置收敛 | chrony、SELinux、firewalld、dnf 源、内核参数、基础包、SSH 加固 | **重复执行零变更**（幂等证明） |
| `deployer` | 部署流水线 | 容器运行时、kubeadm、网络插件、存储、监控接入；**仅 Rocky** | 裸装 Rocky → 集群 Ready 全流程一键复现 |
| `monitoring` | 监控与告警 | exporter 安装注册、scrape 生成、规则管理、通知渠道、静默 | targets 全 UP；告警可触发可恢复 |
| `net` | 网络配置与排障 | `nmcli` 配置、DNS/网关/路由校验、连通性与端口探测、链路诊断 | 预置网络故障可被定位 |
| `diagnose` | 一键体检 | 检查项清单（CPU/内存/磁盘/时间/内核/SELinux/防火墙/证书/日志） | 报告可导出、可对比两次差异 |
| `task` | 编排与审计 | 任务队列、超时、重试、日志流、原始输出留档 | 每次执行都可回放 |

### 5.3 数据模型（初稿）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `hosts` | id, name, ip, os_family, os_version, role, provider, tags, status | 资产主表；`provider` 预留多来源 |
| `tasks` | id, domain, action, targets, status, started_at, ended_at, exit_code | 一次执行 = 一条任务 |
| `task_steps` | id, task_id, seq, name, status, stdout_ref, stderr_ref | 步骤级留证 |
| `artifacts` | id, task_id, path, sha256, size | 原始输出/报告文件 |
| `checks` | id, host_id, check_key, result, detail, checked_at | 体检结果（可做趋势对比）|
| `scrape_targets` | id, job, host_id, port, labels | 监控接入点（含手工加的非 k8s 目标）|

## 6. 关键技术选型与取舍

| # | 决策 | 选用 | 备选 | 理由 | 代价 |
|---|---|---|---|---|---|
| D1 | 后端语言 | **Python 3.12**（RHEL/Rocky 10 自带） | Go | 与既有项目一脉相承；标准库能覆盖 HTTP/SQLite/并发；无需编译分发 | 无静态类型；并发模型要自己想清楚 |
| D2 | HTTP 服务 | **标准库 `http.server` 起手**，能力不够再换 FastAPI | 一上来就 FastAPI/Flask | 管理机只有 4GB，零依赖部署最省事；先跑通再升级 | 路由/中间件要手写；性能不适合高并发（本项目不需要） |
| D3 | 远程执行 | **系统 `ssh` 二进制 + 密钥（BatchMode）**，不引入 paramiko | paramiko / 每台装 Agent | 零依赖；agentless 无侵入；RHEL 系自带 openssh-clients | 无连接池，靠 `ControlMaster` 复用；需处理已知主机校验 |
| D4 | 变更执行 | **双后端：`shell` 后端 + `ansible` 后端（可切换）** | 只做一种 | shell 后端保证「零依赖也能跑」；Ansible 后端保证「幂等 + 可讲」 | 两套剧本要维护；好在剧本是同一份语义 |
| D5 | 数据存储 | **SQLite**（任务/审计/清单/体检） | PostgreSQL / MySQL | 单机零运维；WAL 模式够用 | 并发写要靠队列串行化 |
| D6 | 指标存储 | **Prometheus**（不自己造） | 自研 TSDB | TSDB 是专门问题；Prometheus 是行业事实标准 | 多一个组件要维护（约 300–500MB 内存） |
| D7 | 采集方式 | **exporter 注册表**（node_exporter 起步，预留 windows_exporter / snmp_exporter / 自定义脚本） | 自研采集器 | 这是 R3「为其它系统预留」的落地方式 | exporter 生命周期要管（版本、端口、自启） |
| D8 | 前端 | **原生 HTML/CSS/JS**，SSE 推日志 | Vue/React | 无构建链、无 node_modules；长任务用 SSE 比轮询干净 | 组件复用靠自律 |
| D9 | 可视化 | **交给 Grafana**，控制台只做「跳转 + 结论」 | 自研图表 | 省下大量工期，且 Grafana 图表更专业 | 两套界面的风格不统一 |
| D10 | 任务并发 | **有界线程池 + 队列**，按主机串行、跨主机并行 | 全并行 | 避免同一台机器被两个任务同时改（漂移源头） | 大集群时吞吐偏低（本项目 4 台，无所谓） |

> **D4 是本项目最值得讲的一个取舍**：为什么既做 shell 后端又做 Ansible 后端？因为「零依赖可跑」和「幂等可讲」是两个目标 —— 前者保证任何一台 RHEL 系机器上都能起来，后者保证简历上「自动化」三个字站得住。

## 9. 风险清单（按「一定会踩」排序）

### 9.1 RHEL / Rocky **10** 与 9 代的差异（新版本发行版的真实坑）

| # | 变化 | 影响 | 对策 |
|---|---|---|---|
| 1 | **只有 cgroup v2**，v1 已移除 | kubelet / containerd 必须用 `systemd` cgroup driver；老教程的 `cgroupfs` 直接失效 | 所有 k8s 清单显式指定 `systemd`；开篇就写进基线 |
| 2 | **iptables-legacy 移除**，只剩 nftables 与 `iptables-nft` 兼容层 | kube-proxy 走 nftables 模式；Calico 与 firewalld 抢 nftables 的经典冲突更突出 | 与 firewalld 的协同单独做一节验证；规则落库前先 `nft list ruleset` 取证 |
| 3 | **network-scripts 彻底删除** | 网络配置只剩 NetworkManager / `nmcli`；老 `ifcfg-*` 写法无效 | 控制台网络模块**只走 nmcli** |
| 4 | **DNF5 成为默认包管理器**（`dnf` 指向 dnf5） | 输出格式与部分参数与 DNF4 不同 —— **脚本里解析 `dnf` 输出的地方必坏** | 禁止解析人类可读输出，一律用 `--assumeyes --quiet` + 退出码判断 |
| 5 | **Python 3.12、无 python2** | yum 时代的老运维脚本跑不动 | 只维护 py3 脚本 |
| 6 | **SELinux 默认 enforcing** | 容器挂载、非标准端口、自定义 exporter 端口都可能被拦 | 排障清单必须包含 `ausearch -m avc -ts recent`，且**不允许**一上来就 `setenforce 0` |
| 7 | 内核已是 6.12 一代 | 很多「9 代能用的偏方」要重新验证 | 关键步骤一律实测 + 留原始输出 |

### 9.2 内存吃紧

- 4GB 跑 k8s 节点：可用，但要把 `kubelet` 的 `--kube-reserved/--system-reserved` 设好，避免节点频繁被 OOM。
- 4GB 跑 Prometheus + Grafana + 控制台：**紧**。对策：保留期设 7–15 天、开启 WAL 压缩、限制 Grafana 插件、控制台本身零依赖省内存。**这是 M4 最可能翻车的地方，提前打预防针。**

### 9.3 磁盘与精简置备

- 200 GB 是**上限**不是占用，但 guest 内写满会直接打爆物理盘。
- 对策：guest 内对 `/` 与 `/var` 做容量告警；定期在 Workstation 里 `Clean Up Disks`，必要时 `vmware-vdiskmanager -k` 回收。

### 9.4 NAT 与主机名解析

- NAT 网段 IP 由 DHCP 分配，**可能变**。对策：要么在 NAT 的 DHCP 里做静态绑定，要么 guest 内配静态 IP（**注意别和 DHCP 池冲突**），宿主机 `/etc/hosts` 或本地 DNS 做名字解析。
- 一旦 IP 漂移，Prometheus scrape 与 SSH 清单同时失效 —— 这是「明明昨天还好」类故障的第一嫌疑人。

### 9.5 时间同步

- etcd 与 k8s 证书对时间敏感。chrony 没同步时，症状是「kubeadm 报证书无效」这种看起来毫不相关的错误。
- 对策：`chronyc sources -v` 进体检项，并在部署流水线前置校验「时间偏差 < 1s」。

### 9.6 克隆 / 快照后的身份重复（必踩）

克隆出来的机器会带着爹的身份：

| 要重置的东西 | 命令/位置 |
|---|---|
| machine-id | `truncate -s 0 /etc/machine-id && rm -f /var/lib/dbus/machine-id && systemd-machine-id-setup` |
| SSH host key | `rm -f /etc/ssh/ssh_host_* && ssh-keygen -A` |
| 主机名 | `hostnamectl set-hostname <新名>` |
| IP | `nmcli` 重新配（**别和源机撞**） |
| 虚拟磁盘 UUID（可选） | VMware 里重新生成 |

> 不重置的后果：SSH 报 `Host key verification failed`（看起来像网络问题），systemd 服务身份混乱，监控两台机器傻傻分不清。

### 9.7 Workstation 侧的坑

- 异常退出会留 `.lck` 锁文件 → 虚拟机打不开，删锁即可。
- `vmrun` / `vmcli` / REST API 主要面向**已有 VM**，别指望它从零建机。
- 并发开关机要限速，抢盘会让宿主机整体卡顿。

## 10. 原理速讲（为什么这么设计）

### 10.1 为什么「纳管」而不是「自动建虚拟机」

自动化是有成本的：**每一层自动化都要承担那一层的失败模式**。自动建 VM 意味着软件要懂 VMware 的 vmx 格式、虚拟磁盘格式、注册流程、兼容级别 —— 这些知识只服务一个厂商，且极不稳定（版本一变就废）。而 4 台机器的规模，手工建一次的边际成本接近零。

反过来，把自动化力气花在**配置、部署、监控、排障**上，收益是「与厂商无关、可迁移、可复用」的能力。这就是把 `HostProvider` 做成接口的原因：**信任边界收在「VM 已经存在」这条线上**。

### 10.2 为什么控制台不自己存指标

指标的三个真正难点是：**高写入吞吐、压缩、降采样查询**。这三件事需要专门的存储引擎（TSDB）。自己在 SQLite 里写「每秒一条样本 × 4 台 × 几百个指标」，几天后查询就会慢到不可用。

**原则：软件管「怎么采、采什么、什么时候告警」，不管「样本存哪里」。** 这也是 L4/L5 分层的由来。

### 10.3 为什么 agentless（SSH）而不是每台装 Agent

| | agentless（SSH） | Agent 模式 |
|---|---|---|
| 部署成本 | 零（系统自带 sshd） | 每台装、升级、保活 |
| 防火墙 | 一个端口 | 要开反向连接或额外放行 |
| 实时性 | 请求-响应 | 可长连、可推事件 |
| 状态 | 无状态、易诊断 | 有状态、易失连 |

4 台机器的规模，agentless 的所有缺点都不成立，优点全部命中。**但要注意代价**：SSH 无连接池 → 靠 `ControlMaster` 复用长连接；同时它是「逐台串行」的手感，所以 D10 才要按主机串行。

### 10.4 为什么「幂等」是自动化的生命线

命令式（`mkdir /data`）第二次执行会报错；声明式（`确保 /data 存在`）第二次执行零变更。差别在**可重复性**：

- 非幂等 → 每次调试都改变状态 → 环境逐渐漂移 → 最后没人知道线上是什么样；
- 幂等 → `N` 次执行等价于 `1` 次 → 环境状态 = 代码状态。

**「第二次执行零变更」既是 M3 的验收标准，也是本项目的核心工程信条。**

### 10.5 为什么 NAT 下宿主机能直达 guest

VMware 的 NAT 网络里，**宿主机本身就是那个网段的一员**：它有一张 `VMnet8` 虚拟网卡，既是网关又是 DHCP 服务器。所以「宿主 → guest」是同网段的二层通信，压根没经过 NAT 转换。NAT 只发生在「guest → 外网」方向。

这一点决定了本项目**不需要端口转发**就能纳管，也让「管理流量」与「业务流量」共用一条链路 —— 代价是：**链路本身出问题时，管理通道会一起断**，所以将来若要上生产思路，管理面要独立。

## 11. 常见误区

| # | 误区 | 为什么错 |
|---|---|---|
| 1 | 「先把功能做完，再考虑幂等」 | 幂等不是优化项，是地基。后期补幂等 = 重写剧本 |
| 2 | 「监控能出图就算做完了」 | 告警**能触发、能恢复、不误报**才算完；`for` 抑制、分组、静默是必备项 |
| 3 | 「SELinux 太麻烦，先 setenforce 0」 | 一关就把「会排障」这个能力点直接送掉，面试必被问 |
| 4 | 「虚拟磁盘 200GB 是上限，随便写」 | 精简置备下 guest 写多少，物理盘就少多少；写满宿主机全崩 |
| 5 | 「控制台在本机，不用鉴权」 | 本机单用户确实不需要复杂鉴权，但**至少要绑定 127.0.0.1 或内网地址**，绝不能 `0.0.0.0` 裸奔 |
| 6 | 「克隆一台来用最快」 | 不重置身份 = 给自己埋一个「两天后才发作」的故障 |
| 7 | 「自研比现成的好，显得有技术」 | 自己写 TSDB / 自己写图表 = 把工期烧在没有产出的地方 |

## 12. 自测题（附要点）

1. **为什么监控栈不能放在 k8s 集群里？** → 被监控对象与被监控系统同命；且覆盖不到非 k8s 主机（与 R3 冲突）。
2. **「幂等」和「可重复执行」是一回事吗？** → 幂等强调「多次执行 = 一次执行」，可重复强调「能再跑一遍」，前者更强，是本项目的标准。
3. **RHEL 10 上 kubelet 为什么必须用 systemd cgroup driver？** → 内核只提供 cgroup v2，v2 需要 systemd 来统一管理资源层级，`cgroupfs` 会与 systemd 抢控制权。
4. **NAT 网络下宿主机为什么不用端口转发就能访问 guest？** → 宿主机有 VMnet8 网卡，本身就在 NAT 网段内，是网关+DHCP。
5. **控制台为什么坚持不自己存指标？** → TSDB 的三个难点（吞吐/压缩/降采样）需要专门引擎，重复造轮子没有产出。
6. **SSH agentless 最大的代价是什么？** → 无连接池、请求-响应模型；靠 ControlMaster 复用、按主机串行来缓解。
7. **克隆一台 Rocky 后最少要重置哪三样？** → machine-id、SSH host key、IP（主机名也算）。
8. **告警规则里的 `for` 是干什么的？** → 抑制抖动：条件持续满足一段时间才发通知，避免瞬时毛刺刷告警。
9. **为什么采集器要做成「注册表」而不是写死 node_exporter？** → R3：为其它系统（Windows / SNMP 设备 / 自定义脚本）预留接入能力。
10. **200GB 精简置备磁盘的风险点在哪？** → 上限≠占用，guest 内写满会吃掉物理盘；需要容量告警 + 定期 compact。
