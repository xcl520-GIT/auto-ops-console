## 0. 结论（★ 必须分两半说，别含糊）

| 用户想做 | 能不能 | 依据 |
|---|---|---|
| **AI 帮你把 VM 开机**（不用你手点 VMware） | ✅ **能** | 本机有 `vmrun.exe`，`vmrun -T ws start <vmx>` 已验证可用 |
| 开机后 **AI 进 VM 内部查 / 改** | ✅ **能** | **现有 42 个动作直接复用**，一行不改 |
| 干完 **AI 帮你关回去** | ✅ **能** | `vmrun stop <vmx> soft` |
| 变更前 **AI 帮你打快照**（比文件级备份更强） | ✅ **能** | `vmrun snapshot` |
| ★ **VM 关机状态下，直接读它磁盘里的数据** | ❌ **在当前组合下不能**（见下） | **实测**：Workstation 没有 `vmware-mount` |
| ★ VM 关机状态下**改**磁盘里的东西 | ❌ **不做** | 离线写盘风险极高，虚拟化层不校验，不做默认 |

### 0.1 为什么"关机读盘"在这套环境下没有干净方案（★ 实测，不是推测）

2026-09-25 现场核查 `C:\Program Files (x86)\VMware\VMware Workstation`（VMware Workstation 17.6.3 安装目录）：

| 工具 | 在不在 | 说明 |
|---|---|---|
| `vmrun.exe` | ✅ 在 | 电源 / 快照 / guest 操作（guest 操作要求 **VM 已开机**且 Tools 在跑） |
| `vmware-vdiskmanager.exe` | ✅ 在 | 只能建盘 / 转格式 / 扩容 / 碎片整理 —— **不能挂载** |
| **`vmware-mount.exe`** | ❌ **不在** | 旧版 Workstation 的"映射虚拟磁盘"组件，**已被 VMware 移除**（与新版 Windows 驱动签名冲突） |
| `libguestfs` / `guestfish` | — | 那是 **Linux** 工具链，本机宿主机是 **Windows**，不在 |

→ **所以"关机也能把 VM 磁盘里的数据查出来"这件事，在「VMware Workstation + Windows 宿主机」这个组合下没有原生产品级方案。**

**两条变通路（都可用，但各有代价）**：

| 路线 | 做法 | 代价 / 风险 | 建议 |
|---|---|---|---|
| **A（主推）** | **AI 按需开机 → 干完 → 按需关回**：`vm.start` → 等 SSH 就绪 → 复用现有全部动作 → `vm.stop soft` | **零新增风险**；代价只是"要开机"（但**不需要你手动开机**，是 AI 编排的） | ✅ **默认做这条** |
| B | **救援机挂只读盘**：找一台常开的 Linux VM 当"救援机"，把目标机的 vmdk 作为**第二块盘**挂上去，**只读**挂载后查 | 要改 `.vmx`、要动磁盘拓扑、"只读"要靠人守；且**依然不能改** | ⏳ **先不做**（列可选，等真有"必须不开机"的场景再上） |
| C | **换 / 加 ESXi（vSphere）**：原生支持离线 VMDK 与快照 API | 企业形态，另一个大工程（新平台、新网络、新认证） | ❌ 本阶段不做 |

> ★ 一句话：**正确答案不是"关机也能干所有事"，而是「AI 按需开机 → 干完 → 关回」。**
> 这个形态反而更值钱 —— 它把**"开机/关机的成本"也算进了编排**（用完就关，省资源；像 CI 的临时环境）。

## 2. 为什么这是"天然的一步"（不是新方向）

1. **`设计\01 R5` 早就预留了**：「软件负责纳管，**架构上保留可插拔的 VM Provider**」—— 本话题就是把第一个 Provider 插上。
2. **目标机本来就是本机的 Workstation 虚拟机** → "宿主机"不是一个远端主机，而是**本机自己**。
3. **它接上的是同一套账本与纪律**：新动作照样进 `map.yaml`（覆盖率、权重、缺口一视同仁）。

★ **但它打破了本项目此前的单一执行模型** —— 以前"**一切执行都经 SSH 到 Linux**"，
现在要多一类执行通道：**本机 Windows 进程（`vmrun.exe`）+ 它自己的输出解析**。
这是本话题**最大的架构事件**，必须先写进 `docs\动作规范.md`（新章节）再动代码（沿用"规范先行"铁律）。

## 3. 要新建的五件事

| # | 要建的 | 要点 |
|---|---|---|
| 1 | **宿主机执行通道** | 本机 Windows 进程（**不走 ssh**）：调 `vmrun.exe` / `vmware-vdiskmanager.exe`；输出解析（`vmrun` 输出是裸文本，需专用 parser）；错误翻译（VM 不存在 / 已被占用 / 正在运行…） |
| 2 | **虚拟化层动作（新域 M）** | `vm.list` · `vm.status` · `vm.start` · `vm.stop` · `vm.snapshot-create` · `vm.snapshot-list` · `vm.snapshot-revert` · `vm.ip` |
| 3 | ★ **编排链：「开机 → 等 SSH 就绪 → 自动体检」** | 这是 **T5 Recipe 的第一个真用例**：一步不是动作而是"等条件成立"（轮询 SSH + `hostname` 探针）。★ 复用 `host.enroll` 里已经写好的"轮询校验"逻辑 |
| 4 | ★ **新护栏：变更前打快照** | 与既有"改动前文件备份 / 一键恢复 / 确认闸门"并列 → 护栏从**三件套升为四件套**。虚拟化层快照是**比文件级备份更强的一层**（整机回滚） |
| 5 | **账本与页面** | 域 M 进 `map.yaml`；界面加「**虚拟机**」页签（列表 / 状态 / 电源按钮 / 快照） |

## 4. ★ 风险分级（必须与既有 `green/yellow/red` 对齐，不许自创）

| 动作 | 风险 | 为什么 |
|---|---|---|
| `vm.list` / `vm.status` / `vm.ip` / `vm.snapshot-list` | **green** | 只读 |
| `vm.start` | **yellow** | 可逆（再关掉即可） |
| `vm.stop`（**soft**，走 guest 正常关机） | **yellow** | 可逆；且会调用 Tools 的优雅关机 |
| ★ `vm.stop`（**hard**，等于**拔电源**） | 🔴 **red** | 可能丢数据 → **必须手输确认词**，且**禁止批量** |
| `vm.snapshot-create` | **yellow** | 占磁盘空间（可删） |
| ★ `vm.snapshot-revert`（回滚快照） | 🔴 **red** | 会**丢掉当前状态** —— 与"不做自动回滚"的理由同源：可能把"其实没坏"的现场也覆盖掉 |
| `vm.clone` / `vm.delete` | 🔴 **red** | 见 T17 |

> ★ 一条纪律（**靶子纪律同样适用于虚拟化层**）：
> `D:\VMs` 下有 **14 台 VM，其中 10 台与本项目无关**（monitor-* / node-* / Prometheus* / 原型机-01…）。
> **默认只允许操作「已在 `hosts.yaml` 登记」或「用户当次显式点名」的 VM**；
> 其余一律拒绝（并在错误里说清"这是保护，不是故障"）。

## 5. T17 · 克隆与身份重置（兑现 `设计\01 C5`）

**问题**：克隆出来的 VM 会**身份重复** —— machine-id、SSH host key、IP、主机名、UUID 全都一样。
这会让 `hosts.yaml`、SSH 信任、审计全部串味。

**流程**：`克隆模板 → 自动重置身份 → 自动纳管（复用 host.enroll）→ 自动体检（复用 checkup）`

| 步 | 做什么 | 复用 |
|---|---|---|
| 1 | 克隆（从模板 / 某台机） | 新：`vm.clone` |
| 2 | 开机 + 首次身份重置：`machine-id` / `ssh host key` / 主机名 / 静态 IP | 新动作（`file.*` + 服务重启） |
| 3 | **自动纳管** | ✅ **`host.enroll` 现成**（含"真登录校验"与"写前备份"） |
| 4 | **自动体检** | ✅ **`checkup` 现成**（12 项） |

**价值**：一句话换来一台干净靶子机 —— **「给我来一台干净的 Rocky 10 靶子机」→ 克隆 + 改身份 + 纳管 + 体检，全自动。**

## 6. 与 AI 层（T12~T15）的关系（★ 顺序上 T16 必须在前面）

**AI 只是调用者：它需要"先有虚拟化层的动作"，才能"自己开机去查"。**
所以 T16 应排在 T12 **之前**（若追求"AI 操作关机 VM"的体验）。

到那时对话会长这样：

```
你：查一下那台关掉的 node-02 里有没有 XXX 的配置
AI：目标机 node-03 当前是「关机」状态 —— 查它里面的东西需要先开机。
    预计：vm.start → 等 SSH 就绪（约 40s）→ file.grep → 查完问你要不要关回去。
    要开机吗？            ← ★ AI 不擅自开机，它问
你：（点确认）
AI：…（开机 → 就绪 → 检索 → 汇报定位）… 查完了，要关回去吗？
```

★ 这就是本项目一贯的"**人类在环**"：**AI 不擅自开机，它问** —— 与铁律 9（闸门不许被 AI 代过）同源。

## 8. 明确不做（防范围失控）

1. ❌ **不做离线写盘**（关机状态下改 VM 磁盘）
2. ❌ **不直接改 `.vmx`**（一律经 `vmrun` / 只读读 `inventory.vmls`）
3. ❌ **不碰与本项目无关的那 10 台 VM**（除非用户当次显式点名）
4. ❌ **不替代 VMware GUI 的职责**（虚拟网络编辑器 / vmnet / NAT 规则 —— `设计\01` 已定：软件最多**只读感知**）
5. ❌ **不把"开机"做成默认行为**：开机是有成本的（CPU / 内存 / 磁盘 IO），必须**人点头**（或明确授权"可以开机"）

## 9. 一句话给下一个话题

> 这不是"再加一个功能"，而是**把工作台的手从"能 ssh 到的机器"伸到了"机器的开关"** ——
> 一旦能开关机 + 打快照，**"靶子机"这件事本身就被自动化了**：
> 一句话克隆一台 → 自动改身份 → 自动纳管 → 自动体检 → 用完关掉。
> 而 AI 在这一切之上，只多说了一句话：「**要开机吗？**」
