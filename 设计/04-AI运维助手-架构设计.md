## 0. 一句话结论

> **能实现，而且这是本项目当前"性价比最高的加法"。**
> 原因不是"LLM 很强"，而是：**AI 做运维最难的那一半（可靠的手 + 骗不了的事实校验），本项目已经造好了。**

**LLM 做运维的瓶颈从来不是"会不会说"，而是两件事：**
1. **有没有一双可靠的手** —— 能确定性执行、且执行完能自证；
2. **它骗不骗得了系统** —— 说"已经修好了"时，系统能不能反驳它。

本项目恰好把这两件事都做成了：

| 已有资产 | 为什么它正好是 AI Agent 需要的 |
|---|---|
| **42 个动作 + YAML schema** | 天然就是工具（function/tool）定义 —— 有 `title` / `summary` / `params`（含 `label`/`type`/`pattern`/`help`）。**可以自动导出成模型能用的工具表**，不用手写一套 |
| **参数白名单正则 + argv 数组 + `shlex` 转义** | AI 生成的参数也走**同一套校验** → 命令拼接 / 提示注入**在加载期就被拒**（安全契约三层防线一层都不用改） |
| ★ **`verify` 自证** | AI 最容易出的问题是"说成功了其实没成功"。这里**每条动作必须自证**，自证不过 → 任务判 `failed`。**AI 骗不了系统** |
| **`conclusion` 结论模板** | 喂给模型的**已经是结论**，不是 3000 行终端原文 → 省 token、少幻觉 |
| **`precheck` + `classify_remote_failure`** | 失败被翻译成「原因 + 建议」→ AI 能读懂并决定下一步，而不是瞎猜 |
| **留证 + `ops.db` + 回放** | 每句 AI 的话都能挂一个**任务ID** → 可审计、可复现、可追责 |
| **护栏三件套**（改动前备份 / 一键恢复 / 手输确认词） | 天然的「人类在环」闸门 —— AI 撞到 `red` 就得**停下来等人** |
| **批量 + 失败隔离** | 多机编排天然成立（"去每一台机器里找"这句话不需要新机制） |
| ★ **覆盖率账本 + 权重** | 能回答"**AI 现在会做哪些活、还不会哪些**" —— 商业化时这就是"能力边界可量化"，同类方案少有 |

→ **结论：不需要重写。是"给动作面装一个对话前端 + 一层编排大脑"。**

## 1. 架构分层（AI 不新增一条执行通道）

```
        用户
   ┌──────┴───────┐
   │              │
[点界面按钮]   [说人话]           ← 两种入口，原目标不变 + 加法
   │              │
   │        ┌─────┴──────────────────────────┐
   │        │ AI 侧（本期新建）                │
   │        │  · Agent 运行时（多轮 tool-calling）│
   │        │  · 工具面导出器（catalog → schema）│
   │        │  · 闸门策略（谁能自主、谁要人点）  │
   │        │  · 会话 / 报告 / 双结论对照        │
   │        └─────┬──────────────────────────┘
   │              │
   └──────┬───────┘
          ▼
 ★ 同一套接口层 `/api/**`  ←──── 铁律 8：AI 与点击**同权**，没有后门
          ▼
   执行引擎：预检 → 计划 → 执行 → 自证 → 留证   ← 已有，**不改**
          ▼
   护栏：改动前备份 / 一键恢复 / 确认闸门        ← 已有，**不改**
          ▼
   目标机（系统 ssh）
```

**为什么这条"同一套接口"是承重墙**：
留证、护栏、确认闸门、覆盖率账本**全部长在这条路径上**。
AI 若绕过去（直连 engine / 直连 ssh），这四套体系会**同时失效** —— 而它们正是这个项目全部的信任来源。
→ 已写进总纲 §2 **铁律 8**。

## 3. 工具面导出：怎么把 42 个动作给模型（不让它被淹死）

**问题**：42 个工具 × 每个 5~8 个参数，全量塞进上下文既贵又会让模型挑错。

**做法（三层递进暴露）**：

| 层 | 给模型什么 | 什么时候给 |
|---|---|---|
| L1 域索引 | 12 个域 + 每个域一句话 + 该域动作数 | 永远在上下文里（很短） |
| L2 动作摘要 | 命中的域下，动作的 `id` + `summary` + 风险等级 | 模型先"选域"，再展开该域 |
| L3 完整 schema | 具体动作的完整 `params`（label/type/pattern/help/default） | 模型决定要用它时 |

**要点**：
- 工具描述**直接取自 YAML**，不另写一份（否则又会"两张表漂移"，规范里已踩过同族坑）
- 风险等级（`green`/`yellow`/`red`）**必须**进 schema 描述 → 让模型自己就知道"这个动作我不能擅自跑"
- 参数缺省值可以给它，但要**明确告知"用默认值意味着什么"**（例如 `TOP_N` 默认 20 会看不见第 21 个）

## 4. 权限闸门矩阵（★ 铁律 9 的落地）

| 风险 | AI 能不能自己跑 | 人的角色 | 界面表现 |
|---|---|---|---|
| `green`（只读） | ✅ **自主** | 事后可看报告 | 直接执行，把结论贴回对话 |
| `yellow`（可恢复变更） | ⚠️ **必须先把「要做什么 + 影响面 + 怎么撤」摆给人看**，人点一下才执行 | **点一次** | 对话里出现一张"待确认卡片"（带备份说明） |
| `red`（破坏性） | ❌ **AI 永远不能自主** | **手输确认词** | 卡片要求人**在界面输入确认词**；AI 无法代输 |

**两条硬约束**（写进铁律与自检）：
1. **AI 侧拿不到"确认词"**：确认词只能在界面由人输入，AI 的工具面**不含任何可以传 `confirm_text` 的通道**。
2. **拒绝要说人话**：AI 想跑 `red` 被拒时，不是静默失败，而是明确告诉它"这需要人来确认"，
   让它**转成"请你确认"的自然语言** —— 这样它不会反复重试撞墙（T4 的状态机 bug 就是"撞墙重试"的同族问题）。

## 5. ★ 数据边界（这**不是技术问题，是商业化决策**）

把目标机的原始输出发给云端模型 = **数据出境**。企业客户第一个问题一定是这个。
所以路线图里必须**显式留档位**，不能事后补。

| 档 | 发给模型的内容 | 适合 |
|---|---|---|
| **A（默认 / 最保守）** | **只发 `conclusion`（结论）+ 动作ID + 参数**，**不发原始 stdout** | 任何真实环境起步 |
| **B** | 结论 + **脱敏后**的原文片段（IP/主机名/路径换成占位符） | 需要模型看细节做判断时 |
| **C** | 结论 + **原始输出** | 仅限演示 / 纯实验环境 |
| **D（预留）** | 走**本地模型**（不外流） | 真正私有化交付 |

**默认 A**；B/C 由用户在设置里显式开；D 作为"私有化部署"档位预留。
★ 一个直接收益：**因为动作已经有 `conclusion`，默认档 A 的成本和风险都极低** ——
这是"把结论做成一等公民"这个既有设计的意外红利。

## 6. 会话即证据（数据模型）

```
对话会话 (session)
  └─ 轮次 (turn)
       ├─ 用户说了什么
       ├─ AI 决定调哪些工具（含原因）
       └─ 工具调用 → 落到既有 ops.db 的任务 (task_id)
                        └─ 原始输出 / 自证结果 / 备份记录（**全部已有**）
```

**由此得到三件商业上值钱的东西**：
1. **可导出报告**：一次排障对话 = 一份带证据链的报告（谁会拒绝"AI 帮你干完还附证据"）
2. **故障时间线**：把多个 `task_id` 串成一条"发生了什么 → 查了什么 → 改了什么 → 结果如何"
3. **可复现**：拿同一个会话，能在另一台机器重跑（因为动作是声明式的）

## 7. 约束（AI 版的"九条铁律"，逐条可自检）

1. AI **只走** `/api/**`，无后门（铁律 8）
2. `red` 确认词**只能人输**，AI 侧不提供该通道（铁律 9）
3. **结论以工作台为准**：AI 的说法与 `verify` 冲突时，界面显示工作台的判定，并记录分歧
4. AI **不得**凭空断言"已修复" —— 任何"已修复"必须挂一个 `verify_result == ok` 的任务
5. AI **不得**静默降级：查不到就说**查不到**，并说明查了哪些范围（★ 反例：三台 K8s 没装 `openssl` → 必须说"这项无法判定"，不许编一个结果）
6. API key **不落盘、不进日志、不进 Git**
7. 数据外流**按档位**（默认 A），换档必须由人显式操作
8. 每个 AI 动作都要能**回答"你为什么要跑这个动作"**（保留它选择工具的理由）
9. **多机操作失败要隔离**（沿用既有批量规则：一台失败不拖垮其余），并在报告里逐台列出

## 9. 风险与"不做"清单（诚实版）

### 9.1 三个真风险

1. ★ **"无鉴权 + 只绑本机"这条既有红线，会因为 AI 而变脆**。
   现在的安全性靠"只有本机能用"。一旦 AI 能在对话里执行 `yellow`，那么**任何能跟这个服务说话的东西**
   都等于拿到了执行权。→ 结论：**放开 `yellow`（T14）之前，必须先把鉴权补上**，
   或严格限定"只绑 127.0.0.1 且不对外暴露"。这是本项目**唯一**被 AI 动摇的既有铁律，必须显式处理。
2. **幻觉的具体形态**：不是"编造命令"，而是**编造因果**（"磁盘满了是因为日志，我已经清理了"）。
   → 对策见 §7 第 3/4/5 条；再加一条：**界面必须能一键展开原始输出**，让人自己看。
3. **成本不可控**：多机检索（"去每一台里找"）很容易一次烧掉几万 token。
   → 对策：结果先**聚合再回传**（在本地做去重/计数/截断），别把 4 台的原文都塞给模型。

### 9.2 明确不做（防范围失控）

1. ❌ **不做"AI 直连 ssh"**（等于放弃全部护栏）
2. ❌ **不做无人值守的自动修复**（沿袭既有结论：只做"备份 + 可一键恢复"）
3. ❌ **不做放开 `red` 给 AI**（永远）
4. ❌ **不做跨用户共享记忆**（第一版）
5. ❌ **不替代人做决策**：AI 只负责"查清楚 + 说清楚 + 等你点头"
