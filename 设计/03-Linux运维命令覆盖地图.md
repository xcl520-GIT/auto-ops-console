## 2. 「90%」怎么变成可度量的口径

拍脑袋的 90% 没有被验证的价值。本项目的口径是：

```
覆盖率 = Σ(已界面化的动作 × 该动作的真实使用频次权重)
       ÷ Σ(全部运维动作 × 各自频次权重)
```

三个关键约定：

1. **按「频次」加权，不按命令条数**。`ls` 与 `mkfs` 各算一条命令，但前者一天几十次、后者一年一次。按条数算会得出漂亮的假数字。
2. **分母必须来自真实数据，不能来自我的想象**。三种数据源，按可信度排序：
   - ① 实验机上的 `~/.bash_history` 与 `journalctl` 里的真实操作记录；
   - ② 用户自己的排障手册与知识库（`计算机知识库\`）里出现过的命令；
   - ③ 业界通用的运维命令频次清单（兜底）。
3. **覆盖 = 能完整做完一件事，不是能敲一条命令**。判定标准：**不看终端、不查文档，在界面上从头做到尾**。比如「查一个端口被谁占了」要一次给全：`ss` + 进程 + 归属服务 + 建议。

> 这也是方向正确性的**唯一硬指标**：分母真实、分子可点、差距可算。

### 2.1 「90%」的全景：8 层技术栈（终局打勾表）

上面那个公式要有意义，前提是**分母知道多大**。按运维技术栈拆 8 层：

| 层 | 内容 | 终局 | 当前阶段 |
|---|---|---|---|
| **S1 主机层** | Linux 系统管理（本文件 §3 的 12 个域就是这一层的展开） | ✅ | ✅ **正在做** |
| **S2 服务层** | 中间件与服务的安装/配置/启停/升级/备份（Nginx、MySQL、Redis、Zabbix…） | ✅ | ⏸ 第二阶段 |
| **S3 编排层** | 容器运行时、K8s 集群搭建与管理 | ✅ | ⏸ 第三阶段 |
| **S4 数据层** | 数据库备份恢复、慢查询、主从状态、连接数 | ✅ | ⏸ |
| **S5 可观测层** | 监控 / 告警 / 日志（本身也做成一键部署） | ✅ | ⏸ 第四阶段 |
| **S6 网络层** | 网络配置与排障（S1 里已含诊断部分；此处指跨机拓扑与设备） | ✅ | 🔸 部分在 S1 |
| **S7 安全层** | 基线加固、SELinux / SSH 审计、登录审计 | ✅ | 🔸 部分在 S1 |
| **S8 虚拟化层** | VM 生命周期管理 | ❌ **明确不做**（手工建机 + 纳管） | ❌ |

> **这张表的作用**：将来被问「你说覆盖 90%，覆盖了啥」，直接把 8 层逐层打勾给他看。**只拆 S1 是不够的** —— 服务部署、集群、数据库、监控都是日常运维的大头。

### 2.2 覆盖率怎么记账（地图即账本）

「覆盖率」不能靠感觉，得有个自动对账的装置：

| 做法 | 说明 |
|---|---|
| 地图即账本 | 磁盘上 `catalog/map.yaml` 登记「**应该有什么**」（本文件 §3 的全部条目）；`catalog/actions/*.yaml` 是「**已经有什么**」 |
| 自动对账 | 程序启动/刷新时对账，算出**每一层、每一域、每个风险等级、每个优先级**的实现率 |
| 界面呈现 | 首页显示：`已实现 23 / P0 登记 25（主机层 92%）`，并按域列出**缺口清单** |
| 为什么这么做 | ① 进度可见 ② **缺口可见**（不会「做了很多但不知道还差什么」）③ 换话题接手时一眼看清差在哪 |

## 3. Linux 运维命令覆盖地图（12 个域）

> 风险等级：🟢 只读｜🟡 可恢复的变更｜🔴 破坏性
> 优先级：**P0** 方向验证必须做｜**P1** 第一阶段补全｜**P2** 后续｜**P3** 长尾（留命令逃生口即可）

### 域 A · 系统与主机

| 命令族 | 界面形态 | 风险 | 优先级 |
|---|---|---|---|
| `hostnamectl` `uname -r` `cat /etc/os-release` `uptime` `lscpu` `free -h` | **主机概览卡片**（一屏给全） | 🟢 | **P0** |

| `shutdown` `reboot` `systemctl isolate` | 关机/重启（🔴 二次确认 + 影响面提示） | 🔴 | P2 |
| `hostname` `/etc/hosts` | 主机名与本地解析编辑 | 🟡 | P1 |

## 4. 第一阶段（M2）建议范围：**只做 P0，约 25 个动作**

「只读 + 高频 + 一次给全结论」，足够验证方向，也足够第一次感到比敲命令快。

**诊断查询类（15）**
1. 主机概览（CPU/内存/负载/发行版/内核/运行时长）
2. 时间与时区同步状态
3. 磁盘用量总览（df + inode）
4. 目录体积排行
5. 大文件查找
6. 进程总览（排序/过滤/进程树）
7. 服务总览（谁在跑、谁失败、失败原因）
8. 日志查看器（unit/时间/级别/关键字 + 流式）
9. 端口占用查询（端口 → 进程 → 服务）
10. 网卡与地址总览
11. 路由表与邻居表
12. DNS 解析链路诊断
13. 连通性与路径诊断（ping/traceroute）
14. 内核日志与 OOM 检索
15. SELinux 状态 + 近期 AVC

**查询类（3）**
16. 防火墙规则查看
17. 已装软件与文件归属（rpm/dnf 查询）
18. 包搜索 / "哪个包提供这个命令"

**动作类（7）**
19. 服务启停重启 / 自启管理
20. 文件上传下载（单机 + 多机分发）
21. 文件内容检索与下载
22. 多机批量执行
23. 执行历史与回放
24. 关键文件改动前自动备份
25. 一键体检（把上面若干项打包成报告）

> 这 25 个动作覆盖的正是「日常运维 90% 时间花在哪」的那部分。做完它们，方向对不对就能用真实体验回答了。

## 5. 方向正确性的三个自检问题（做完 M2 就回答）

| # | 问题 | 通过标准 |
|---|---|---|
| 1 | **不看终端能不能干完活？** | 25 个动作里有 ≥ 20 个能「从界面开始、到拿到结论结束」，中途不需要切终端 |
| 2 | **加一个新动作的成本够低吗？** | 新动作只写一份 YAML + 一个输出模板，**不改核心代码** |
| 3 | **覆盖清单是数据说了算吗？** | 分母来自真实 history / 手册统计，而不是我列的想象清单；覆盖率能在界面上看到 |

**配套机制：覆盖率看板** —— 界面上直接显示「已覆盖 X / 共 Y 个动作（按频次加权 Z%）」。方向对不对，一眼可查。

## 6. 明确排序（方向不砍，先后有别）

```
第一阶段（现在）  Linux 运维命令界面化  ← 验证方向
      ↓
第二阶段          服务目录（Nginx/MySQL/Docker/Redis…一键部署）
      ↓
第三阶段          K8s 全生命周期（建集群 + 集群管理）
      ↓
第四阶段          监控告警接入（从 v0.1 的主角降为一项服务）
```

**注意一个架构红利**：动作台和服务目录**共用同一个执行引擎**。第一阶段把引擎做扎实，第二阶段加服务只是「写配方」，不是重写系统。所以现在只做动作台**不是缩水，是打地基**。
