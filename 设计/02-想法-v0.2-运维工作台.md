## 1. 定位修正：v0.1 想偏了

| | v0.1（想偏了） | **v0.2（修正后）** |
|---|---|---|
| 一句话 | 纳管 → 基线 → 部署 → 监控 → 排障的**流水线** | 把**运维操作本身**变简单的**工作台** |
| 主角 | Prometheus 告警、证据链、幂等剧本 | **常用运维动作** + **服务一键部署** + **集群管理** |
| 监控告警 | 是核心能力 | **降级**：变成服务目录里的一个条目（和 Nginx 平级） |
| 用户体感 | 「配好一次，长期收敛」 | **「少敲命令，少记步骤，点一下就跑」** |
| 面向对象 | SRE / 平台工程 | **一线运维的日常** |
| 典型场景 | 集群漂移 2 秒内被 GitOps 收敛 | 我要装个 Nginx / 我要重启 Zabbix / 我要把第 4 台机器加进 k8s |

**结论**：v0.1 的架构分层大体还能用，但**重心要整个挪**。而且优先级要重排 —— 先做「好用」，再做「完备」。

## 2. 一句话定位（v0.2）

> **一个跑在管理机上的本地 Web 工作台：把手敲的运维命令变成「可选、可预览、有护栏」的动作，把 Nginx / MySQL / Docker / Zabbix / K8s 这类服务的搭建部署压缩成「选服务 → 填参数 → 一键跑完」，并且能直接在界面里管 K8s 集群。**

它是**运维领域的「应用商店 + 遥控器」**。

> 目录名建议从 `auto-ops-console` 改为 **`ops-workbench`（运维工作台）** —— 现在是改名最便宜的时刻。

## 3. 三块核心能力

### 3.1 动作台 · 把「我记得要敲什么」变成「选一下就跑」

**要覆盖的场景**（都是运维第一反应要做的事）：

| 类别 | 动作举例 |
|---|---|
| 服务 | 启/停/重启/自启开关、状态、失败原因、上次日志尾 |
| 日志 | 看某个 unit 的日志、按时间/关键字/级别检索、导出 |
| 磁盘 | 用量总览、目录排行、大文件查找、inode 检查 |
| 进程与端口 | 端口占用是谁、进程树、资源占用 TOP |
| 网络 | IP/路由/DNS/网关校验、连通性、端口探测、抓包辅助、网卡状态 |
| 安全面 | firewalld 规则查看与放行、SELinux 状态与近期 AVC、用户与 sudo |
| 系统 | 时间同步校验、包管理（查/装/卸/更新）、内核参数、定时任务、主机名/hosts |
| 批量 | 多机同时执行同一动作、文件分发、结果横向对比 |

**关键设计：不是把命令原样搬上网页。** 每条动作是一份声明式描述：

```yaml
id: svc.restart
title: 重启服务
risk: yellow                # green=只读 / yellow=可恢复 / red=破坏性
params:
  - { name: unit, type: service_name, required: true }
preview: "systemctl restart {{unit}}"     # 跑之前先给你看命令原文
impact: "该服务会短暂中断，约 1–3 秒"
precheck:
  - check: unit_exists
  - check: unit_is_active
verify:
  - check: unit_is_active                   # 跑完自证，不是“我点过了”
audit: true
```

四个护栏：**风险分级**（红色必须二次确认）、**命令预览**（先看后跑）、**执行前预检**（不满足就早失败，别跑一半）、**执行后自证**（用系统事实验证结果，不靠"应该成功了"）。

> 这条「动作描述」和下面的「服务配方」**共用同一套执行引擎** —— 这是本项目的技术核心，也是最大的架构收敛点。

### 3.2 服务目录 · 一键搭建部署

**目标服务清单（分三批）**：

| 批次 | 服务 | 说明 |
|---|---|---|
| 第一批 | **Nginx、Docker/containerd、MySQL(或 MariaDB)、Redis、NFS** | 最常用、依赖少、容易做成闭环 |
| 第二批 | **Kubernetes**（见 3.3）、**Zabbix**、**Prometheus + Grafana**、**HAProxy / Keepalived** | 有跨机协同与可视化 |
| 第三批 | PostgreSQL、MinIO、GitLab（重）、RabbitMQ/Kafka、Jenkins | 按需 |

**每个服务是一张「配方（recipe）」，声明式 YAML，磁盘上可读可改**：

```yaml
id: nginx
name: Nginx
version_pin: "1.26.x"          # 必须锁版本，否则“昨天能装今天不能”
engines: [package, container]  # 两条路：dnf 装 / 容器跑，用户选
resources: { cpu: 1, mem_mb: 256, disks: ["/var/www:20G"] }
ports: [80, 443]
preflight:
  - { check: port_free, args: [80, 443] }
  - { check: selinux_allow_httpd }
steps:
  - { name: 安装,       action: dnf.install,      args: { packages: [nginx] } }
  - { name: 生成配置,   action: template.render,  args: { src: tpl/nginx.conf.j2, dest: /etc/nginx/nginx.conf }, notify: restart }
  - { name: 放行防火墙, action: firewalld.open,   args: { services: [http, https], permanent: true } }
  - { name: 启动并自启, action: systemd.ensure,   args: { unit: nginx, state: started, enabled: true } }
health:
  - { http.get: "http://127.0.0.1:80/", expect: 200 }
rollback:
  - { action: systemd.stop,   args: { unit: nginx } }
  - { action: files.restore,  args: { from: "${backup_dir}/etc-nginx" } }
```

**「配置模板 + 参数」是简化的关键**：用户只面对 5–8 个填空题（端口、数据目录、密码、允许来源…），YAML/conf 的细节由模板承担。

**每个配方必须成对给出反向操作**：停止 / 卸载（**保留数据** vs 全删，两个按钮）/ 备份与恢复。只写正向步骤的配方是不合格的 —— 那叫「一键装机」，不叫「一键部署」。

**双引擎（`package` / `container`）** 是这个设计里最值得讲的取舍：同一服务两条路，配置生成、数据目录、端口、防火墙放行都要各自处理；好处是「能装得下」和「能讲得出」都成立。

### 3.3 K8s 全生命周期 · 从装到管

**阶段一：装运行时** —— containerd、内核参数、cgroup v2 前提检查、镜像源。
**阶段二：建集群** —— 初始化第一个控制面 → 自动生成 join 命令 → 把剩余节点拉进来 → 装网络插件（Calico）→ 存储类 → 连通性验证。**用户只填 3 个空：哪些机器做控制面、哪些做工作节点、Pod 网段。**
**阶段三：日常管理（这块最值钱，也最容易做得比 kubectl 好用）**

| 域 | 能做什么 |
|---|---|
| 节点 | 状态、标签、污点、**驱逐(drain)/恢复**、资源水位 |
| 工作负载 | 列表与详情、**扩缩容**、重启、**滚动更新与回滚**、换镜像版本 |
| Pod | 日志**流式**看、**进容器 exec**、端口转发、事件时间线 |
| 配置与存储 | ConfigMap / Secret / PVC 的增删改、容量与绑定状态 |
| 排障 | Pod 卡 `Pending` / `CrashLoopBackOff` 时，**直接给成因清单**（资源不足 / 污点 / 镜像拉不到 / PVC 未绑定 / 探针失败 / 调度约束），而不是只丢一段 describe 原文 |
| 集群健康 | 证书到期检查、组件状态、节点版本漂移、升级预检 |

**交互形态**：**「表单 + 结果」为主，「kubectl 原样命令」作为逃生口**。不把高级用户锁死在表单里 —— 否则一旦界面不支持某个操作，整个工具就被弃用。

## 4. 什么叫「简单」——把它拆成可验收的 4 条

| # | 「简单」的具体含义 | 验收方式 |
|---|---|---|
| 1 | **不用记**：不需要背命令和参数 | 常用动作全部有表单，字段带说明与默认值 |
| 2 | **不用怕**：危险动作有护栏、有预览、有回滚点 | 红色动作二次确认率 100%；关键动作有备份 |
| 3 | **不用查**：结果直接给结论，不是给你一堆原文 | 失败时输出「原因 + 下一步建议」，而不是只有 stderr |
| 4 | **不用串**：多步骤流程一次跑完 | 从裸机到 Nginx 可用 / 到 K8s Ready 都是「一次点击」 |

## 5. 架构调整（相对 v0.1 的增删）

```
表现层   工作台界面（动作面板 / 服务目录 / 集群管理 / 任务流 / 审计）
             │  HTTP + SSE
接口层   本地 HTTP 服务（127.0.0.1 或内网，绝不 0.0.0.0 裸奔）
             │
领域层   ┌ action   动作库（语义化封装 + 护栏）
         ├ catalog  服务配方引擎（★ 技术核心）
         ├ k8s      集群生命周期管理
         ├ inventory 资产与连通性（保留）
         ├ task     编排与审计（保留，权重提高）
         ├ diagnose 体检（并入 action）
         └ monitoring 监控告警（★ 降级为服务目录里的一项）
             │
执行层   Recipe/Action Engine（预检 → 计划 → 逐步执行 → 自证 → 留证）
         HostProvider（workstation / 静态清单 / 未来 vCenter）
         Transport（系统 ssh + 密钥，零依赖）
         Executor（shell 后端 / ansible 后端，可切换）
             │
数据层   SQLite（清单 / 任务 / 审计 / 体检 / 操作历史）
         指标时序 → 交给 Prometheus（不自己造 TSDB）
```

**新增的两个最重要概念**：

- **Action（动作）**：原子操作，带风险等级、预览、预检、自证。
- **Recipe（配方）**：由多个 Action 组成的服务部署方案，带版本锁定、参数表单、健康检查、回滚。

**统一执行引擎**是整套系统的收敛点：动作台和 k8s 管理台底下跑的是同一套「预检 → 计划 → 执行 → 自证 → 留证」管道。

## 6. 必须提前想清楚的 10 个难题（也是面试最容易被追问的地方）

| # | 难题 | 思路 |
|---|---|---|
| 1 | 「一键部署」容易，「一键还原」难 | 配方强制声明回滚点；卸载给「保留数据 / 全删」两个选项 |
| 2 | 幂等 | 重复部署 = 收敛到目标状态，第二次零变更（沿用 v0.1 的生命线） |
| 3 | 版本漂移 | 镜像 tag 与包版本显式锁定，禁止 `latest` |
| 4 | 跨主机协同（k8s 必须） | 配方支持「角色」概念：哪些步骤在控制面跑、哪些在工作节点跑 |
| 5 | 容器 vs 包管理双引擎 | 同一服务两条实现路径，配置/数据/端口/防火墙各自处理 |
| 6 | 危险操作 | 红/黄/绿分级 + 预览 + 二次确认 + 审计留痕 |
| 7 | 界面追不上 CLI 的能力 | 必须留「原样命令」逃生口，且执行结果同样入审计 |
| 8 | 不重复造轮子 | Zabbix/Prometheus/Grafana 用自己的 Web，控制台只负责「装好 + 给入口 + 健康检查」 |
| 9 | 单机 4GB 管理机 | 后端标准库优先、前端无构建链、监控组件调小（Prometheus 保留期 7 天） |
| 10 | 扩展性 | 配方是磁盘上的 YAML，用户能照着样例自己加服务 —— 这是这套东西能活下去的前提 |

## 7. 优先级重排（先「好用」，再「完备」）

| 阶段 | 目标 | 交付感 |
|---|---|---|
| **M1** | 环境就绪：4 台 VM + 系统 + 基线快照 | 有机器可玩 |
| **M2** | **动作台最小可用**：10–15 个高频动作 + 风险分级 + 预览 + 审计 | **第一次感到「比敲命令快」** |
| **M3** | **配方引擎** + 第一批服务（Nginx、Docker、MySQL、Redis） | **第一次感到「不用记安装步骤了」** |
| **M4** | **K8s 配方**：装运行时 + 一键建集群 | 裸机 → Ready |
| **M5** | **K8s 管理台**：扩缩容 / 重启 / 回滚 / 日志 / exec / 驱逐 | **第一次感到「不用开终端管理集群」** |
| **M6** | 第二批服务（Zabbix、Prometheus+Grafana、HAProxy/Keepalived）+ 监控告警接入 | 服务目录成形 |
| **M7** | 护栏、审计、证据、演示手册 | 可交付、可讲 |

## 8. 验收标准（测试版）

| 能力 | 可量化验收 |
|---|---|
| 动作台 | ≥ **15** 个动作；100% 有风险分级与命令预览；红色动作 100% 二次确认；每次执行可回放 |
| 服务目录 | ≥ **4** 个服务走完「填参数 → 部署 → 健康检查通过 → **幂等重跑零变更** → 卸载（可选保留数据）」全流程 |
| K8s 建集群 | 裸装 Rocky → 集群 Ready **一次点击**完成，全程有日志与原始输出；重复执行不破坏集群 |
| K8s 管理 | 界面内完成 **6** 件事且全程不碰终端：扩容、重启、回滚、看日志、进容器、驱逐节点 |
| 排障体验 | ≥ **5** 个预置故障（端口占用 / 防火墙拦截 / SELinux 拒绝 / DNS 失败 / 磁盘写满），界面**给出根因与建议**，而不是只回显 stderr |

## 9. 与 v0.1 需求基线的关系（没被推翻的部分）

原基线 R1–R8 **继续有效**，只是优先级与角色变了：

| 原基线 | v0.2 下的角色 |
|---|---|
| R1 系统矩阵（RHEL 10 + Rocky 10，不支持 CentOS） | 不变，仍是动作台与配方的作用对象 |
| R2 k8s 只对 Rocky 开放 | 不变 |
| R3 监控告警为其它系统预留扩展点 | 降级：先作为服务目录中一项，扩展点保留 |
| R4 规模 ≤4 台 / 4GB / 200GB | 不变 |
| R5 VM 由用户手工建，软件纳管 | 不变（而且更合理了：工作台的活是「操作已有机器」） |
| R6 全部 NAT、网络由软件管理 | 不变，且网络动作是动作台的重点板块 |
| R7 本地 Web 控制台 | 不变 |
| R8 先出设计文档 | 已交付，本文件是第二轮 |
